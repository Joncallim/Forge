# SPEC-0009: Trigger/Event Envelope v1

**Status:** Accepted
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the Trigger and event occurrence model, CloudEvents-compatible envelope, causality tracking, deduplication, loop prevention, and schedule catch-up semantics.

## Definitions

- **Trigger**: A declarable event source or condition that may request an Execution.
- **Trigger occurrence**: A single concrete event instance produced by a Trigger.
- **CloudEvents**: A specification for describing event data in a common way (CNCF).
- **Causation**: The chain of events and operations that led to this occurrence.
- **Dedupe**: Prevention of duplicate processing from the same occurrence.
- **Loop prevention**: Detection and prevention of self-triggering or recursive trigger cycles.

## Normative requirements

### R1: CloudEvents compatibility

Trigger occurrences MUST be representable in CloudEvents-compatible format with the following required attributes:

| Attribute | Description |
|---|---|
| `id` | Unique occurrence identity |
| `source` | Trigger identity that produced the occurrence |
| `specversion` | CloudEvents spec version (1.0) |
| `type` | Forge-specific event type (e.g., `forge.trigger.schedule`, `forge.trigger.webhook`) |
| `subject` | Subject of the occurrence (e.g., Mission id) |
| `time` | Timestamp of the occurrence |
| `datacontenttype` | Content type of the data payload |
| `dataschema` | Schema of the data payload |

### R2: Forge extensions

In addition to CloudEvents attributes, every Trigger occurrence MUST carry these Forge extensions:

| Extension | Description |
|---|---|
| `forge:trigger_id` | Trigger definition identity and revision |
| `forge:mission_id` | Mission this occurrence relates to |
| `forge:execution_id` | Execution this occurrence relates to (if applicable) |
| `forge:principal` | Principal that authenticated the event source |
| `forge:authentication_state` | How the event source was authenticated |
| `forge:resource_refs` | Resources referenced by this occurrence |
| `forge:correlation_id` | Correlation identity for tracing |
| `forge:causation_id` | Identity of the event/operation that caused this occurrence |
| `forge:caused_by_operation_id` | Operation identity that caused this occurrence |
| `forge:dedupe_key` | Key used for deduplication |
| `forge:policy_version` | Policy version at occurrence time |
| `forge:schema_version` | Schema version of the occurrence |

### R3: Authentication and authorization separation

Authentication of the event source (verifying who sent the event) MUST be separate from authorization to act (whether the source is permitted to trigger the resulting Execution).

A Trigger occurrence MUST be authenticated before being authorized.

### R4: Storage truth

PostgreSQL MUST be the authoritative store for Trigger occurrence truth.

Redis MAY be used for transport, wakeup, and temporary caching.

A Redis failure MUST NOT cause permanent loss of occurrence state.

### R5: Deduplication

Each Trigger definition MUST declare its deduplication strategy:

| Strategy | Description |
|---|---|
| `exact_match` | Same `dedupe_key` within window is duplicate |
| `idempotent` | Repeated delivery is safe; idempotency handled downstream |
| `coalesce` | Multiple occurrences within window are merged into one |
| `latest_only` | Only the most recent occurrence within window is processed |

Dedupe window and policy MUST be part of the Trigger definition.

### R6: Trigger occurrence identity vs Operation identity

Trigger occurrence identity prevents duplicate **execution intent**.

Operation identity (SPEC-0004 R5) separately prevents duplicate **side effects**.

Both identities MUST be preserved and distinguished.

An occurrence may produce multiple Operations; each Operation has its own identity.

### R7: Causality tracking

Every Trigger occurrence MUST record its causal linkage to Forge external Operations.

When an Operation produces an event that triggers a new occurrence, the `causation_id` and `caused_by_operation_id` MUST be set on the new occurrence.

### R8: Loop prevention

Forge MUST detect and prevent self-triggering loops.

Default behavior: a Trigger occurrence whose `causation_id` matches a recent occurrence from the same Trigger in a bounded window MUST be discarded or flagged.

Explicit recursive or cyclic Trigger flows MUST require:

- Bounded maximum depth.
- Bounded occurrence count.
- Bounded budget.
- Bounded wall-clock time.

### R9: Schedule catch-up policies

Schedule-based Triggers MUST declare a catch-up policy for missed occurrences:

| Policy | Behavior |
|---|---|
| `skip` | Missed occurrences are dropped; only the next scheduled occurrence fires |
| `latest` | Only the most recent missed occurrence is processed (coalescing) |
| `bounded` | A bounded number of missed occurrences are processed in order |

`skip` is the default. Unlimited catch-up replay is PROHIBITED.

### R10: Zero-token idle

A Trigger with no pending occurrences MUST consume zero model tokens.

Schedule evaluation (checking whether it's time to fire) MUST be deterministic and token-free.

### R11: Filter before model wake

Deterministic filters and change-detection logic MUST run before a model is woken for Trigger processing.

Patterns like "every hour → model → 'nothing changed'" are PROHIBITED.

## Data/state model

### trigger_definitions table

```
id: UUID
mission_id: UUID
trigger_type: enum(schedule, webhook, event, resource_change)
name: string
description: string | null
config: jsonb (type-specific configuration)
dedupe_strategy: enum(exact_match, idempotent, coalesce, latest_only)
dedupe_window_ms: int
catch_up_policy: enum(skip, latest, bounded) | null
max_occurrences_per_window: int | null
max_depth: int | null (for recursive flows)
enabled: bool
policy_revision: int
created_at: timestamptz
updated_at: timestamptz
```

### trigger_occurrences table

```
id: UUID
trigger_id: UUID
mission_id: UUID
execution_id: UUID | null
cloud_events_id: string
cloud_events_source: string
cloud_events_type: string
subject: string | null
time: timestamptz
data: jsonb | null
forge_extensions: jsonb
dedupe_key: string | null
correlation_id: UUID
causation_id: UUID | null
caused_by_operation_id: UUID | null
processing_state: enum(received, deduplicated, queued, processing, completed, failed, loop_prevented)
received_at: timestamptz
processed_at: timestamptz | null
```

## Authority implications

- A Trigger must have a Grant for the `trigger.activate` Capability on its Mission.
- Authentication of the event source is separate from authorization to act.
- A Trigger cannot widen the authority of the Mission it triggers.

## Failure semantics

- Occurrence persistence failure → event is lost; source MUST retry if supported.
- Deduplication failure → occurrence may be processed or dropped depending on failure mode.
- Loop detection → occurrence is discarded and logged.
- Schedule catch-up exceeding bounds → occurrences are dropped; operator alert is raised.

## Concurrency semantics

- Occurrence processing MUST be serialized per Trigger definition to prevent race conditions.
- Deduplication checks MUST be atomic.
- Causality chain MUST be immutable after recording.

## Security/privacy

- Occurrence data MUST be classified according to its content (SPEC-0005).
- Webhook authentication MUST use standard mechanisms (HMAC, TLS client certs, OAuth).
- Loop detection MUST NOT leak occurrence data.

## Compatibility/versioning

- CloudEvents specification version is part of the occurrence schema.
- New Forge extensions MUST be added without breaking existing consumers.

## Observability/evidence

- Every occurrence state transition MUST be recorded.
- Deduplication and loop prevention events MUST be logged.
- Schedule evaluation is deterministic and MAY omit logging for unchanged evaluations.

## Conformance requirements

- C1: Occurrences conform to CloudEvents format with Forge extensions.
- C3: Occurrence state survives restart.
- C4: Deduplication is atomic and correct under concurrent delivery.
- C5: Authentication and authorization are separate checks.
- C7: Zero-token idle is maintained between occurrences.

## Non-goals

- Real-time event streaming beyond Trigger dispatch.
- Complex event processing (CEP).
- External event bus integration beyond webhook/API.
- Distributed Trigger coordination across Forge instances.

### R12: Redis reconstruction from PostgreSQL

When Redis state is lost or corrupted, Trigger occurrence truth MUST be reconstructed from PostgreSQL (the authoritative store). The reconstruction mechanism follows SPEC-0014 migration principles:

- PostgreSQL is the source of truth for occurrence state.
- Redis state is a cache/transport projection.
- Reconstruction is triggered by the #347 durable wakeup mechanism.
- Reconstruction MUST NOT change the authoritative occurrence state in PostgreSQL.
