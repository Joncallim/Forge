# SPEC-0008: Conformance Test Standard v1

**Status:** Accepted
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the conformance test classification system, mandatory test types for each feature, failure injection requirements, property/invariant testing rules, and the criteria for closing a phase with required conformance evidence.

## Definitions

- **Conformance test**: An executable test that proves whether an implementation satisfies one or more normative requirements from a spec.
- **Test class**: A category of conformance test with specific objectives and pass criteria.
- **Failure injection**: A test that deliberately induces a failure mode to verify correct handling.
- **Property/invariant**: A condition that must always hold true across all states and transitions.
- **Residual uncertainty**: Known gaps in test coverage that are explicitly documented rather than ignored.

## Normative requirements

### R1: Test classes

Every spec requirement MUST be testable by one or more of these conformance test classes:

| Class | Objective | Typical approach |
|---|---|---|
| **C1 — Contract/schema** | Verify API contracts, input/output schemas, data formats | Schema validation, type checks, boundary value tests |
| **C2 — Determinism/property** | Verify deterministic behavior and invariants | Property-based testing, invariant checks, idempotency tests |
| **C3 — Persistence/restart/replay** | Verify correct behavior across crashes, restarts, and replay | Crash injection, restart tests, replay with same inputs |
| **C4 — Concurrency/race/fencing** | Verify correct behavior under concurrent access | Race condition tests, lease fencing tests, parallel execution |
| **C5 — Authority/security** | Verify authorization, grant boundaries, and security controls | Permission escalation tests, deny-override tests, fail-closed tests |
| **C6 — Privacy/egress/secrets** | Verify data classification, egress controls, and secret containment | Sentinel-secret leakage tests, egress policy tests |
| **C7 — Cost/token/budget** | Verify budget enforcement, cost accounting, and token tracking | Budget limit tests, unknown-cost tests, zero-token-idle tests |
| **C8 — End-to-end/release** | Verify complete workflows and release readiness | Integration tests, release gate tests, scenario tests |

### R2: Requirement-to-class mapping

Every spec MUST declare which conformance test classes apply to each normative requirement.

Implementation PRs MUST include tests for all applicable classes, or explicitly document which classes are deferred and why.

### R3: Failure injection requirements

Every consequential side-effect path MUST inject failures at each of these stages:

1. Before durable intent is recorded.
2. After durable intent but before external submission.
3. During external submission.
4. After external acceptance but before local acknowledgement.
5. After local acknowledgement.
6. Process crash at each of the above points.
7. Lease expiry during execution.
8. Duplicate delivery.
9. Stale worker execution.
10. Cancellation during each phase.
11. Revocation during each phase.
12. Reconciliation failure.

### R4: Zero-token-idle proof

Any feature claiming zero-token operation MUST instrument all model call paths and prove:

```
model_call_count == 0
```

Source inspection alone is insufficient. Tests MUST instrument the actual invocation boundary and fail if a model call occurs during idle periods.

### R5: Property/invariant tests

The following invariants MUST be tested by property-based or invariant-checking tests:

1. Child Grant never exceeds parent Grant authority envelope.
2. Spent + reserved ≤ hard budget ceiling at all times.
3. Terminal Operation cannot return to a non-terminal state.
4. Confirmed idempotent Operation cannot duplicate external effect.
5. Revoked Principal cannot obtain new admission.
6. Unknown evidence cannot be forged into pass/zero.
7. Self-verification cannot grant authority.
8. A producer cannot independently verify itself.
9. Stale/unknown/missing evidence never becomes success.
10. A lower classification resource cannot declassify a higher one through derived artifacts.

### R6: Phase closure requirements

A major phase (spec or implementation milestone) closes only when:

1. All required conformance test classes for the phase's specs pass.
2. CI is green for the relevant test suites.
3. Hostile/failure-injection fixtures pass.
4. Migration and restart recovery is proven.
5. Residual uncertainty is documented.

### R7: Test isolation

Conformance tests MUST be isolated from each other.

Tests MUST NOT depend on the side effects of other tests.

Tests MUST clean up their state or use isolated fixtures.

### R8: Evidence recording

Test results MUST produce evidence artifacts that can be inspected.

Test evidence MUST include:

- Test identity and class.
- Spec requirements being tested.
- Inputs and expected outputs.
- Actual result.
- Pass/fail status.
- Timestamp and test environment.

## Data/state model

### conformance_test_registry (conceptual)

```
test_id: string
spec_ref: string (e.g., "SPEC-0003 R5")
class: enum(C1, C2, C3, C4, C5, C6, C7, C8)
description: string
invariant: string | null
failure_injection_stage: string | null
automated: bool
last_run_at: timestamptz
last_result: enum(pass, fail, skipped)
```

## Authority implications

- Conformance tests that prove authority invariants (C5) are critical release gates.
- A failing C5 test MUST block release.

## Failure semantics

- Test infrastructure failure → tests MUST be re-runnable and produce deterministic results.
- Flaky tests MUST be quarantined and fixed before being treated as authoritative.

## Concurrency semantics

- Tests MAY run in parallel if they use isolated fixtures.
- Tests that share state MUST be serialized.

## Security/privacy

- Conformance tests MUST NOT use production credentials or data.
- Sentinel-secret tests MUST use synthetic secrets, not real ones.

## Compatibility/versioning

- Tests are versioned with the spec they test.
- When a spec version changes, tests for the old version MUST still be runnable against historical evidence.

## Observability/evidence

- Test results are evidence artifacts.
- Test coverage per spec requirement MUST be measurable.
- CI MUST report conformance test class coverage.

## Conformance requirements

- C1: This spec itself — the test classification system MUST be documented and consistently applied.

## Non-goals

- Mandating a specific test framework.
- Requiring 100% line coverage.
- Defining test environment requirements beyond isolation.
