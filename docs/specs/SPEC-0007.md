# SPEC-0007: Error & Reason Codes v1

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the error and reason code taxonomy for all Forge components. Machine consumers MUST use stable codes, not human-readable prose, for programmatic decision-making.

## Definitions

- **Reason code**: A stable, namespaced string identifier for a specific failure or denial condition.
- **Error contract**: The structured payload returned when an operation cannot be completed.
- **RFC 9457**: Problem Details for HTTP APIs — a standard format for machine-readable error responses.

## Normative requirements

### R1: Code namespace hierarchy

All reason codes MUST use a dot-separated namespace hierarchy.

Initial namespaces:

| Namespace | Scope |
|---|---|
| `auth.*` | Authentication failures |
| `policy.*` | Policy evaluation failures |
| `grant.*` | Grant-related denials |
| `internal.*` | Internal system errors for diagnostics/audit only. MUST NOT be returned to external callers — map to a safe public error code before crossing the service boundary. |
| `resource.*` | Resource access failures |
| `budget.*` | Budget exhaustion or errors |
| `provider.*` | Provider availability or configuration errors |
| `model.*` | Model invocation failures |
| `operation.*` | Operation execution failures |
| `side_effect.*` | Side-effect lifecycle errors |
| `execution.*` | Execution lifecycle failures |
| `mission.*` | Mission lifecycle failures |
| `queue.*` | Queue and dispatch errors |
| `trigger.*` | Trigger processing errors |
| `verification.*` | Verification and gate errors |
| `gate.*` | Gate evaluation failures |
| `package.*` | Workforce package errors |
| `adapter.*` | Capability adapter errors |
| `migration.*` | Migration failures |
| `security.*` | Security violations |

### R2: Code stability

A shipped stable reason code MUST NOT have its semantic meaning changed.

Deprecated codes MUST remain recognizable and MUST NOT be reused with a different meaning.

New codes MAY be added within any namespace.

### R3: Error contract structure

Errors MUST be exposed in RFC 9457-compatible form where practical:

```json
{
  "type": "urn:forge:error:<namespace>:<code>",
  "title": "Human-readable short title",
  "status": 403,
  "detail": "Human-readable explanation",
  "instance": "urn:forge:operation:<operation_id>",
  "forge:reason_code": "grant.denied",
  "forge:retryable": false,
  "forge:reconciliation_required": false,
  "forge:operator_action": "Review grant and re-approve",
  "forge:evidence_ref": "urn:forge:evidence:<uuid>",
  "forge:safe_display": true,
  "forge:causal_entities": {
    "grant_id": "uuid",
    "mission_id": "uuid"
  }
}
```

### R4: Required error fields

Every error MUST include:

| Field | Description |
|---|---|
| `forge:reason_code` | Stable namespaced reason code |
| `forge:retryable` | Whether the caller may retry the same operation |
| `forge:safe_display` | Whether the detail may be displayed to non-operator users |

### R5: Retryable classification

`retryable: true` means the same request MAY succeed if retried without modification (e.g., rate limit, temporary outage).

`retryable: false` means retrying the same request will produce the same failure (e.g., missing grant, invalid input).

`submission_uncertain` errors MUST have `reconciliation_required: true` and `retryable: false`.

### R6: Machine-consumer rule

Machine consumers (automated retry logic, routing decisions, budget enforcement) MUST NOT parse human `detail` or `title` fields. All programmatic decisions MUST use `forge:reason_code`.

### R8: Safe display classification

Every error MUST declare whether its detail is safe to display to users who are not operators.

`safe_display: false` errors MUST be replaced with a generic message in non-operator contexts.

## Data/state model

### reason_codes registry (conceptual)

```
namespace: string
code: string
full_code: string (namespace.code)
http_status: int | null
default_title: string
default_detail: string
retryable_default: bool
reconciliation_required_default: bool
safe_display: bool
stable_since: date
deprecated: bool
deprecated_at: date | null
```

This registry MAY be maintained as documentation/code rather than a database table.

## Authority implications

- Error codes MUST NOT reveal information that could be used to bypass security controls.
- `security.*` codes MUST have `safe_display: false`.

## Failure semantics

- Unknown error → generic `internal.error` code, `retryable: false`, `safe_display: false`. This code is an internal audit/diagnostics label only. A sanitized safe public error MUST be produced before crossing the service boundary.
- Error code lookup failure → same as unknown error (`internal.error`, `safe_display: false`).

## Concurrency semantics

N/A — error codes are static definitions.

## Security/privacy

- Error messages MUST NOT leak credentials, internal paths, or configuration details.
- `safe_display: false` errors MUST be intercepted before reaching non-operator API responses.
- Stack traces MUST NOT appear in production error responses.

## Compatibility/versioning

- Reason codes are append-only. Deprecation replaces `stable_since` with `deprecated_at`.
- A code's semantic meaning MUST NOT change after it is shipped.

## Observability/evidence

- Every error response MUST be logged with its full reason code and causal entity references.
- Error frequencies MUST be measurable for SLO tracking (see SPEC-0015).

## Conformance requirements

- C1: All errors use stable namespaced reason codes.
- C1: Error contracts include all required fields.
- C5: `safe_display: false` errors are not exposed to non-operators.
- C5: Machine consumers do not parse human-readable fields.

## Non-goals

- Internationalized error messages.
- Real-time error aggregation.
- Custom user-defined reason codes.
