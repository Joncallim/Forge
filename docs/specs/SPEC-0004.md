# SPEC-0004: Operation & Side-Effect Semantics v1

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the Operation Catalog, side-effect lifecycle, idempotency and reconciliation semantics, and the stable Operation identity model for all consequential Forge actions.

## Definitions

- **Operation**: A concrete deterministic action or read performed by Forge or an adapter.
- **Operation Catalog**: A versioned registry of all known Operations with their schemas, capabilities, and policies.
- **Side effect**: Any Operation that mutates state outside Forge's own database.
- **Effect class**: A classification of an Operation's side-effect profile.
- **Retry class**: A classification of an Operation's retry safety.
- **Submission uncertainty**: The state where an external system may or may not have accepted a request due to transport failure.
- **Reconciliation**: The process of determining the actual outcome of a submission-uncertain Operation.
- **Compensation**: An Operation that reverses or mitigates the effects of a prior Operation.

## Normative requirements

### R1: Operation declaration

Every Operation in the Catalog MUST declare:

| Field | Description |
|---|---|
| `operation_id` | Stable identity string (namespaced, e.g., `git.status.read`) |
| `version` | SemVer version of this Operation definition |
| `capability` | The Capability required to execute this Operation |
| `supported_resource_types` | Resource types this Operation can act upon |
| `risk_class` | low / medium / high / critical |
| `input_schema` | JSON Schema 2020-12 defining valid inputs |
| `output_schema` | JSON Schema 2020-12 defining valid outputs |
| `effect_class` | See R2 |
| `retry_class` | See R3 |
| `timeout_policy` | Default timeout, maximum timeout |
| `cancellation_policy` | Whether in-flight work can be cancelled |
| `reconciliation_policy` | How to resolve submission_uncertain states |
| `network_requirement` | none / local_only / outbound_only / bidirectional |
| `credential_requirement` | Whether credentials are needed and which type |
| `confinement_requirement` | Whether execution must happen in a confined environment |
| `evidence_policy` | What evidence is retained, redacted, for how long |

### R2: Effect classes and risk classification

Operations MUST be classified into exactly one effect class AND exactly one risk class. These are independent dimensions — an operation may be low-risk but irreversible (e.g., posting a timestamp to an immutable log) or high-risk but reversible (e.g., temporarily disabling a non-critical service).

**Effect class** (describes mutation scope):

| Class | Meaning | Examples |
|---|---|---|
| `pure` | No side effects; deterministic output from input | Hash computation, schema validation |
| `read` | Reads external state without mutation | Git status, file read, API GET |
| `local_mutation` | Mutates local Forge-managed state | Database write, artifact store |
| `external_reversible_mutation` | Mutates external state; reversal is possible | Creating a draft PR, adding a comment |
| `external_mutation` | Mutates external state; reversal is not guaranteed | Merging a PR, sending email, creating a production issue |

**Risk class** (describes consequence severity — independent of effect class):

| Class | Meaning | Examples |
|---|---|---|
| `low` | No material consequence if misused | Reading public metadata, posting to internal log |
| `medium` | Minor consequence; manual remediation possible | Creating a draft PR, adding a comment |
| `high` | Significant consequence; remediation is complex or costly | Merging a PR, modifying production config |
| `critical` | Severe consequence; may have legal/financial/security impact | Deleting resources, modifying access controls, financial transactions |

Every Operation in the Catalog MUST declare both an effect class and a risk class (see R1). The R1 risk_class field uses this risk classification.

### R3: Retry classes

Operations MUST be classified into exactly one retry class:

| Class | Meaning | Retry behavior |
|---|---|---|
| `replay_safe` | Re-execution produces the same result; no external side effect | May retry unconditionally |
| `idempotent_with_key` | External system supports idempotency keys | Retry with same key |
| `reconcile_before_retry` | Must determine actual state before deciding to retry | Reconcile first, then retry if not confirmed |
| `at_most_once` | Must never produce more than one external submission | Retry only if the request definitively never reached the external system (i.e., `denied` or `failed_before_submission` with certainty); if submission may have occurred, escalate to operator |
| `human_required` | Retry requires explicit operator decision | Escalate to operator |

### R4: Side-effect lifecycle (branching state graph)

Every Operation with an external side effect (effect classes external_reversible_mutation, external_mutation) MUST traverse the following branching state machine. Operations with effect classes pure, read, or local_mutation do not traverse this lifecycle — their execution is either successful (completed) or failed, without submission uncertainty or reconciliation semantics.

Every consequential external side-effect Operation MUST traverse the following branching state machine. Unlike a linear chain, this graph represents mutually exclusive paths and fault-injection points at every transition.

```
requested
  │
  ├──→ denied
  │     (policy/grant/budget checks failed;
  │      no adapter execution occurred;
  │      safe to retry if admission conditions change;
  │      at_most_once Operations MAY retry if the request
  │      definitively never left Forge)
  │
  └──→ admitted (passed policy/grant/budget checks)
       → executing (adapter is performing the action)
            │
            ├──→ failed_before_submission
            │     (error occurred before any external request was sent;
            │      safe to retry according to retry class;
            │      at_most_once Operations that definitively never
            │      reached an external system MAY be retried)
            │
            └──→ submitted
                  (request durably sent to external system;
                   HTTP transport success is NOT automatically
                   business confirmation)
                       │
                       ├──→ confirmed
                       │     (external system acknowledged success per the
                       │      Operation's declared confirmation policy;
                       │      response passed schema validation and was
                       │      durably recorded before Forge acknowledged
                       │      completion to the caller)
                       │
                       ├──→ confirmed_failure
                       │     (external system received the request and
                       │      returned a definitive failure: rejected
                       │      precondition, conflict, permission denied,
                       │      invalid request, etc.;
                       │      NOT submission_uncertain — the outcome is
                       │      definitively known;
                       │      retry semantics depend on the specific
                       │      failure reason and retry class)
                       │
                       ├──→ submission_uncertain
                       │     (transport failure after submission;
                       │      outcome unknown — crash after remote
                       │      acceptance but before durable local
                       │      confirmation;
                       │      MUST NOT be blindly retried)
                       │       │
                       │       └──→ reconciling
                       │             (actively determining actual outcome
                       │              via read-after-write, idempotency
                       │              key check, external audit log
                       │              inspection, or operator review)
                       │                  │
                       │                  ├──→ reconciled_success
                       │                  │     (confirmed success after
                       │                  │      reconciliation)
                       │                  │
                       │                  ├──→ reconciled_failure
                       │                  │     (confirmed failure after
                       │                  │      reconciliation)
                       │                  │
                       │                  └──→ human_required
                       │                        (operator must determine
                       │                         outcome)
                       │
                       └──→ human_required
                             (direct escalation if confirmation policy
                              cannot be evaluated or reconciliation is
                              impossible)
```

#### Transition rules

1. **requested → denied**: Policy/grant/budget checks fail. No adapter execution occurs. The Operation has a definitive terminal outcome (`denied`) and MUST NOT be retried automatically unless admission conditions explicitly change. `at_most_once` Operations that definitively never left Forge MAY be retried after admission conditions are resolved.

2. **requested → admitted**: Policy/grant/budget checks pass.

3. **admitted → executing**: The adapter begins performing the action. If the adapter crashes before any external submission, recovery produces `failed_before_submission`.

4. **executing → failed_before_submission**: Error occurred before the request reached the external system. Safe to retry according to retry class (R3). The Operation MUST NOT be considered submitted. For `at_most_once` Operations: a request that definitively never reached an external system MAY be retried — the "at most once" guarantee applies to external submission, not to internal pre-submission attempts.

5. **executing → submitted**: The request was durably sent to the external system. HTTP-level success (200 OK) does NOT constitute business confirmation. Submission requires evidence that the request left Forge's process boundary.

6. **submitted → confirmed**: The external system acknowledged success per the Operation's declared confirmation policy. For asynchronous systems, this may require remote status polling, read-after-write verification, or idempotency key confirmation. The response MUST pass schema validation and be durably recorded before Forge acknowledges completion.

7. **submitted → confirmed_failure**: The external system received the request and returned a definitive failure response (e.g., 4xx status indicating rejection, precondition failure, conflict, permission denied). The outcome is definitively known — this is NOT `submission_uncertain`. Retry depends on the failure reason: transient precondition failures MAY be retried; permanent authorization failures MUST NOT be retried automatically.

8. **submitted → submission_uncertain**: Transport failure after submission. The request may or may not have been received. This MUST NOT be treated as `failed_before_submission` or `confirmed_failure`. Crash after remote acceptance but before durable local confirmation produces `submission_uncertain` on recovery.

9. **submission_uncertain → reconciling**: The system actively determines actual outcome. Reconciliation strategy depends on the Operation's declared reconciliation policy.

10. **reconciling → reconciled_success / reconciled_failure**: Reconciliation produced a definitive answer.

11. **reconciling → human_required**: Reconciliation could not determine the outcome. Operator must investigate.

12. **submitted → human_required**: Direct escalation when confirmation policy cannot be evaluated.

#### Confirmation policy requirements

Each Operation's confirmation policy MUST declare what constitutes confirmation:

- **Synchronous**: Successful HTTP response with valid response body.
- **Idempotency-key-based**: External system confirms this is the first or only execution of this key.
- **Read-after-write**: Subsequent read confirms the intended state change.
- **Polling**: Asynchronous job reaches success state.
- **External audit**: External system audit log shows the Operation completed.

#### Fault-injection reasoning

Every transition above is subject to process crash at the boundary. The recovery behavior is:

| Crash point | Recovery state | Rationale |
|---|---|---|
| Before `submitted` (admission/denied) | `denied` or `failed_before_submission` | No external side effect possible |
| After `submitted` but before `confirmed` or `confirmed_failure` | `submission_uncertain` → `reconciling` | External side effect may exist |
| During `reconciling` | Re-reconciliation (idempotent) | Reconciliation is itself idempotent |
| After `confirmed` | Terminal `confirmed` | Outcome is known |
| After `confirmed_failure` | Terminal `confirmed_failure` | Outcome is known |
| During `executing` with active lease | Lease expiry → abort → `submission_uncertain` | Adapter MUST abort and report state

### R5: Stable Operation identity

Every consequential Operation MUST have a stable business identity (`operation_run_id`) that is:

- Immutable once created.
- Independent of the entity that requested it.
- Usable as an idempotency key for external systems that support it.

### R6: Submission uncertainty rules

A timeout or transport error after the Operation was submitted to the external system MUST produce `submission_uncertain`, not `failed_before_submission` (see R4 state graph).

An `submission_uncertain` Operation MUST NOT be blindly retried.

An `submission_uncertain` Operation MUST enter `reconciling` state where the adapter determines the actual outcome through:

- Read-after-write verification.
- Idempotency key checking.
- External system audit log inspection.
- Operator review (as last resort).

Process crash after remote acceptance but before durable local confirmation MUST produce `submission_uncertain` on recovery, not generic `failed` or `failed_before_submission`.

### R7: Confirmation rules

An external side-effect Operation is `confirmed` only when:

- The external system returns a success response within the timeout, AND
- The response passes schema validation, AND
- The response is durably recorded before Forge acknowledges completion to the caller.

### R8: Timeout semantics

A timeout after confirmed submission MUST NOT be treated as failure-before-submission.

A timeout MUST abort the Operation's signal/context.

The adapter MUST be given a bounded grace period to settle after timeout signal before Forge records the terminal state.

### R9: Idempotency key usage

If the external API supports idempotency keys, Forge MUST use the stable Operation identity as the idempotency key.

The key MUST be unique per Operation and MUST NOT be reused across different Operations.

### R10: Compensation

Compensation Operations MAY exist for `external_reversible_mutation` and some `external_mutation` classes.

A compensation MUST NOT be automatically applied without operator or policy approval for Operations with risk class `high` or `critical` (see R2 risk classification).

Compensation does NOT change the risk class of the original Operation. An irreversible action is not made low-risk because a compensation exists.

### R11: Operation Catalog immutability

The Operation Catalog is append-only for historical versions.

An existing Operation definition MUST NOT be mutated. Changes create a new version.

Deprecated Operations MUST remain readable for historical evidence reconstruction.

### R12: Input validation

Every Operation MUST validate its inputs against the declared input schema before execution.

For Operations with external side effects (effect classes external_reversible_mutation, external_mutation): validation failure MUST produce `failed_before_submission` with a stable reason code, as no external request was sent.

For `pure`, `read`, and `local_mutation` Operations: validation failure MUST prevent execution and produce a terminal error outcome with a stable reason code. These Operations do not use the `failed_before_submission` state as they have no external submission lifecycle.

## Conceptual data model

### operation_catalog table (definition)

```
operation_id: string (namespaced, e.g., "git.status.read")
version: string (SemVer)
capability: string
supported_resource_types: string[]
risk_class: enum(low, medium, high, critical)
input_schema: jsonb
output_schema: jsonb
effect_class: enum(pure, read, local_mutation, external_reversible_mutation, external_mutation)
retry_class: enum(replay_safe, idempotent_with_key, reconcile_before_retry, at_most_once, human_required)
timeout_policy: jsonb { default_ms, max_ms }
cancellation_policy: jsonb { cancellable: bool, grace_ms }
reconciliation_policy: jsonb { strategy, max_attempts }
network_requirement: enum(none, local_only, outbound_only, bidirectional)
credential_requirement: string | null
confinement_requirement: string | null
evidence_policy: jsonb { retention_days, redact: bool }
deprecated: bool
deprecated_at: timestamptz | null
```

### operation_runs table (execution)

```
id: UUID
operation_id: string
operation_version: string
admission_id: UUID (link to admission/grant check)
principal: string
resource_type: string
resource_selector: jsonb
input_digest: string (SHA-256)
output_digest: string | null (SHA-256)
effect_class: string
retry_class: string
lifecycle_state: enum(requested, denied, admitted, executing, completed, failed, failed_before_submission, submitted, confirmed, confirmed_failure, submission_uncertain, reconciling, reconciled_success, reconciled_failure, human_required)

**Effect-class-dependent semantics**: Operations with effect class `pure`, `read`, or `local_mutation` use a subset: requested → admitted → executing → completed | failed. They do not traverse the external-submission states (submitted, confirmed, confirmed_failure, submission_uncertain, reconciling, reconciled_success, reconciled_failure, human_required). Operations with effect class `external_reversible_mutation` or `external_mutation` use the full R4 state set above.
idempotency_key: string | null
external_trace_id: string | null
started_at: timestamptz
terminal_at: timestamptz | null
evidence_refs: string[] (UUIDs of evidence artifacts)
```

## Authority implications

> **Note:** The data models above are conceptual and show required semantic fields. The exact physical table layout, column types, indexes, and partitioning are implementation decisions. See the [Data Model Reference](data-model-reference.md) for ownership and consolidation.



- Every Operation requires an explicit Grant for its Capability on the target Resource.
- Operation execution is subject to budget checks (see SPEC-0006).
- Operations with risk class `critical` MAY require additional approval beyond the base Grant.

## Failure semantics

- Crash before `submitted` → safe to retry (idempotent or never-begun).
- Crash after `submitted` but before `confirmed` → `submission_uncertain` on recovery.
- Crash during `reconciling` → re-reconciliation on recovery (idempotent).
- Lease expiry during `executing` → adapter MUST abort and report state for reconciliation.

## Concurrency semantics

- Operation identity uniqueness MUST be enforced at the database level.
- Idempotency key uniqueness MUST be enforced.
- Reconciliation MUST be serialized per Operation identity.

## Security/privacy

- Operation inputs and outputs MAY contain sensitive data. Evidence policy MUST specify redaction rules.
- Credentials MUST NOT be stored in Operation records.
- External trace IDs MUST NOT leak internal state.

## Compatibility/versioning

- Existing ADR 0011 (Operation Catalog) and `operation_runs` table are the v1 implementation of this spec.
- New Operation versions MUST be backward-compatible for readers of historical runs.

## Observability/evidence

- Every lifecycle state transition MUST be recorded.
- `submission_uncertain` and `reconciling` states MUST produce operator-visible alerts.
- Evidence artifacts MUST reference the Operation run identity.

## Conformance requirements

- C1: Operation Catalog entries include all required fields.
- C3: Crash recovery produces correct lifecycle state.
- C4: Idempotency key uniqueness prevents duplicate side effects.
- C5: Grant check precedes Operation execution.
- C6: Credentials not leaked in Operation records.

## Non-goals

- Automatic compensation execution without policy approval.
- Distributed transaction coordination across Operations.
- Real-time Operation status streaming.
