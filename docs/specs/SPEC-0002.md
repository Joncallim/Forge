# SPEC-0002: Runtime Contract v1

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the canonical ontology, lifecycle states, and identity rules for Forge VNext runtime entities. It governs all components that create, mutate, or interpret Mission, Execution, Work Package, Agent Run, Operation, Resource, Capability, Grant, Principal, Artifact, Gate, Trigger, Budget, Policy, and Workforce instances.

## Definitions

- **Mission**: A durable desired outcome or responsibility. It may be finite (complete a feature) or persistent (monitor infrastructure health).
- **Execution**: One bounded attempt or cycle pursuing a Mission. A finite Mission produces exactly one Execution per attempt; a persistent Mission produces many Executions over its lifetime.
- **Workflow**: A reusable orchestration template that defines the structure of an Execution.
- **Work Package**: A dependency-scoped unit of work inside an Execution, assigned to one Agent Run or set of Operations.
- **Agent Run**: One bounded invocation of a model or agent runtime, consuming a context packet and producing structured artifacts. The cognitive session (model context, conversation history) is ephemeral. A durable Agent Run receipt captures identity, routing snapshot, token/cost usage, and provenance linkage for evidence and audit.
- **Operation**: A concrete deterministic action or read performed by Forge or an adapter (see SPEC-0004).
- **Resource**: A thing Forge may read, reason about, or affect (repository, document corpus, mailbox, service, database, etc.).
- **Capability**: A class of action that may be permitted (e.g., `filesystem.read`, `github.pr.create`, `mail.send`).
- **Grant**: A binding of Capability to Resource scope under constraints and policy for a Principal (see SPEC-0003).
- **Principal**: An identity acting in Forge — operator, Mission, Execution, Agent Run, Trigger, adapter, verifier, system controller.
- **Artifact**: A durable output or evidence with provenance, revision, and content digest.
- **Gate**: A trusted policy decision evaluated over evidence, producing pass, rework, human_required, or blocked.
- **Trigger**: A declarable event or condition that may request an Execution (see SPEC-0009).
- **Budget**: Hard and soft limits governing spend, tokens, calls, time, retries, concurrency, and depth (see SPEC-0006).
- **Policy**: A versioned set of deterministic rules constraining routing, grants, gates, budgets, egress, autonomy, or recovery.
- **Workforce**: A versioned organisation of roles, workflows, prompts, schemas, policies, and evaluations (see SPEC-0010).

## Normative requirements

### R1: Entity relationships

The canonical relationship MUST be:

```
Mission (0..N Executions over its lifetime)
  ├── Trigger (0..N, bound to Mission; produces/requests Executions)
  ├── Resource (0..N, bound at Mission level)
  ├── Workforce (exactly one, pinned)
  ├── Policy (one or more, applied)
  ├── Budget (exactly one, governing)
  │
  └── Execution (0..N)
        ├── Work Package (0..N)
        │     ├── Agent Run (zero or more)
        │     └── Operation (zero or more)
        ├── Artifact (zero or more, produced)
        ├── Gate (zero or more, evaluated)
        ├── Resource (0..N, snapshot or refinement of Mission bindings)
        ├── Grant (zero or more, issued for this Execution)
        └── Budget (exactly one, governing this Execution,
                    constrained by Mission budget)
```

**Key relationship rules**:
- A Mission MAY have zero Executions (e.g., draft, waiting, or paused state).
- A Trigger is bound to a Mission, not to an Execution. A Trigger occurrence MAY request a new Execution.
- Resource bindings at the Mission level are durable; Executions MAY snapshot or refine them.
- Workforce, Policy, and Budget at the Mission level constrain all Executions under that Mission.
- Grants are issued per Execution within the Mission's authority envelope.

### R2: Lifecycle versus outcome

Executable or stateful entities (Mission, Execution, Work Package, Operation) MUST have a separate **lifecycle state** and **outcome**. These MUST NOT be conflated into a single compound status string.

A lifecycle state describes where the entity is in its progression. An outcome describes the result of a terminal or observable phase.

Resource, Capability, Policy definition, Agent Run (transient), and other non-executable definitional entities MUST NOT carry artificial outcome fields. Their lifecycle is their definition lifecycle (created, updated, deprecated, superseded), not an execution outcome.

**Note on Agent Run**: An Agent Run's cognitive session (model context, conversation) is ephemeral and MUST NOT be treated as durable evidence. However, a durable **Agent Run receipt** MUST be persisted containing: stable identity, parent Work Package/Execution, routing snapshot (cognitive class, provider, model), token/cost usage, produced Artifact provenance references, and terminal state (completed, failed, cancelled). This receipt provides the evidence and audit trail for what model was invoked, at what cost, and what it produced — without requiring permanent conversation state. The Agent Run receipt does NOT carry a separate outcome field; its terminal state is its lifecycle state. The durable outcome of the work is captured by the parent Work Package or Operation.

### R3: Mission lifecycle

A Mission MUST support at least these lifecycle states:

| State | Meaning |
|---|---|
| `draft` | Being defined; not yet active |
| `active` | Pursuing the Mission; Executions may be created |
| `waiting` | Healthy quiescence; no active Execution, no model context, zero tokens consumed |
| `paused` | Operator-suspended; no new Executions, existing ones may complete or be cancelled |
| `terminal` | Mission processing has concluded; no further Executions |

A persistent Mission MAY transition between `active` and `waiting` repeatedly. A finite Mission MUST NOT leave `terminal`.

The terminal result of a Mission is captured in its separate `outcome` field (R5a), not in the lifecycle state. The lifecycle only tracks progression through processing stages.

### R4: Execution lifecycle

An Execution MUST support at least these lifecycle states:

| State | Meaning |
|---|---|
| `created` | Recorded but not yet evaluated for admission |
| `admitted` | Passed initial admission checks; queued for dispatch |
| `queued` | Waiting for capacity/budget/worker |
| `leased` | Assigned to a worker with a time-limited lease |
| `running` | Worker is actively processing |
| `waiting` | Healthy quiescence within an Execution (e.g., awaiting approval gate) |
| `terminal` | Final state; no further processing |

An Execution MUST NOT leave `terminal`.

### R5: Execution outcomes

An Execution outcome MUST be one of:

| Outcome | Meaning |
|---|---|
| `succeeded` | All gates passed; Mission advanced |
| `failed` | An unrecoverable error occurred |
| `cancelled` | Explicitly cancelled before completion |
| `blocked` | Cannot proceed without operator intervention |
| `indeterminate` | Outcome cannot be determined (e.g., ambiguous side effect, lost evidence) |

`indeterminate` MUST NOT be treated as success or failure by downstream policy. It MUST require operator or recovery workflow review.

### R5a: Mission outcomes

A terminal Mission MUST carry an outcome separate from its lifecycle state:

| Outcome | Meaning |
|---|---|
| `succeeded` | Mission objective achieved |
| `failed` | Mission objective could not be achieved |
| `cancelled` | Explicitly cancelled before completion |

The Mission outcome is derived from its constituent Execution outcomes but is not necessarily identical — an operator or policy MAY assign a different Mission-level outcome after review.

**Recoverable blocking and indeterminacy**: An Execution may terminate with `blocked` or `indeterminate` outcome (R5) while its parent Mission remains non-terminal (active, waiting, or paused). These outcomes indicate operator attention is needed but the Mission itself has not failed — it may produce new Executions once the block is resolved or the indeterminacy is reconciled. A Mission MUST NOT be terminal with `blocked` or `indeterminate` outcome; those conditions belong in an actionable blocker/attention field on the non-terminal Mission.

### R6: Gate results

A Gate result MUST be one of:

| Result | Meaning |
|---|---|
| `pass` | Evidence satisfies policy; gate is clear |
| `rework` | Evidence shows deficiencies; work must be revised |
| `human_required` | Policy cannot decide; operator must review |
| `blocked` | Gate cannot evaluate due to missing evidence or policy error |

### R7: Identity rules

Every entity MUST have a stable opaque identity (UUIDv7 or equivalent).

Identity MUST be immutable for the lifetime of the entity.

Identity MUST NOT encode semantic meaning (no embedded type, status, or hierarchy).

Identity MUST be unique within the Forge instance.

### R8: Artifact versioning and provenance

Artifacts MUST be immutable once created.

Each Artifact MUST carry:

- Content digest (SHA-256).
- Revision number (monotonic per logical artifact identity).
- Provenance: creator Principal, creating Execution/Work Package, creation timestamp.
- Content type and encoding.

An updated artifact creates a new revision; old revisions MUST remain readable.

### R9: Timestamps

All persistent timestamps MUST be UTC with explicit timezone annotation.

Schedule-related times MUST use IANA timezone identifiers.

Lease expiry MUST use authoritative clock semantics (database clock preferred over worker clock).

Monotonic duration measurements MAY use local monotonic clocks, but MUST NOT be persisted as authoritative evidence.

### R10: Database mapping

Not every ontology concept requires a separate database table. The implementation MAY coalesce entities where:

- The lifecycle and outcome are the same (e.g., Operation state is part of the Operation record, not a separate table).
- The entity is purely transient (e.g., an Agent Run cognitive session context).
- The entity is a projection or view of another entity.

However, Mission, Execution, Work Package, Agent Run receipt (identity, routing, cost, provenance linkage), Artifact, Gate result, Grant, and Operation MUST have durable storage.

The existing `agent_runs` table is the foundation for the Agent Run receipt. It MUST be extended with routing snapshot, token/cost usage, and provenance linkage fields rather than creating a parallel receipt table.

### R11: `waiting` semantics

The `waiting` state represents healthy quiescence. It MUST NOT imply a live model session.

A recurring Mission in `waiting` between Executions MUST consume zero model tokens.

A Trigger occurrence MAY transition a persistent Mission from `waiting` to `active`.

### R12: Compound status prohibition

No executable/stateful entity MUST use a compound status string that conflates lifecycle state and outcome (e.g., "running_failed", "queued_succeeded").

Lifecycle state and outcome MUST be separate fields for entities covered by R2.

## Conceptual data model

### Mission

```
id: UUID
title: string
description: string
lifecycle_state: enum(draft, active, waiting, paused, terminal)
outcome: enum(succeeded, failed, cancelled) | null
workforce_id: UUID (pinned package revision)
policy_revision: int
budget_id: UUID
parent_mission_id: UUID | null
created_at: timestamptz
updated_at: timestamptz
terminal_at: timestamptz | null
```

### Execution

```
id: UUID
mission_id: UUID
lifecycle_state: enum(created, admitted, queued, leased, running, waiting, terminal)
outcome: enum(succeeded, failed, cancelled) | null
workflow_id: string
workflow_revision: int
budget_reservation: jsonb
principal: string
created_at: timestamptz
leased_at: timestamptz | null
terminal_at: timestamptz | null
```

### Work Package

```
id: UUID
execution_id: UUID
dependency_scope: string
role: string | null
lifecycle_state: enum(pending, running, terminal)
outcome: enum(succeeded, failed, cancelled, blocked) | null
created_at: timestamptz
terminal_at: timestamptz | null
```

Work Package uses lifecycle/outcome separation consistent with Mission and Execution. The lifecycle (`pending → running → terminal`) tracks processing progression; the outcome records the terminal result. This enables separate querying of "is it done?" vs "how did it end?" without conflating them into a single status string.

### Artifact

```
id: UUID
logical_id: UUID (stable across revisions)
revision: int
provenance: jsonb { creator, execution_id, work_package_id, timestamp }
digest: string (SHA-256)
content_type: string
storage_ref: string
created_at: timestamptz
```

### Gate

```
id: UUID
execution_id: UUID
gate_definition: string
result: enum(pass, rework, human_required, blocked)
evidence_artifact_id: UUID | null
evaluated_by: string
policy_revision: int
evaluated_at: timestamptz
```

## Authority implications

> **Note:** The data models above are conceptual and show required semantic fields. The exact physical table layout, column types, indexes, and partitioning are implementation decisions. See the [Data Model Reference](data-model-reference.md) for ownership and consolidation.



This spec does not directly introduce new authorities. It defines the entities that Grant, Capability, and Resource concepts attach to. See SPEC-0003.

## Failure semantics

- If the process crashes during Execution creation after Mission update but before Execution persistence, the Mission state remains consistent. The scheduler MUST re-evaluate pending work.
- If the process crashes after Execution is `admitted` but before it is `queued`, the Execution remains in `created`/`admitted`. Recovery MUST re-evaluate admission.
- If a lease expires while the worker holds it, the Execution MUST return to `queued` or be marked `failed`/`blocked` depending on side-effect evidence.
- An Execution in `running` that loses its worker MUST NOT be automatically retried without evidence review.

## Concurrency semantics

- Leases MUST use fencing tokens or equivalent to prevent stale workers from mutating state after lease expiry.
- Execution dispatch MUST be protected by advisory locks or equivalent to prevent duplicate leasing.
- Gate evaluation MUST be idempotent; the same evidence evaluated twice MUST produce the same result.

## Security/privacy

- Entity identities MUST NOT expose semantic information.
- Mission titles and descriptions MUST be treated as potentially sensitive; see SPEC-0005 for classification rules.

## Compatibility/versioning

- Existing Project and Task concepts remain compatibility surfaces. They MUST map to Mission/Execution semantics internally.
- A non-coding Mission MUST NOT require a fake Git repository or project path.

## Observability/evidence

- Every lifecycle state transition for Mission, Execution, and Work Package MUST produce an audit event.
- Gate evaluations MUST produce durable evidence linking the policy revision, evidence artifact, and result.
- Entity state MAY be exported for telemetry but telemetry loss MUST NOT change entity truth.

## Conformance requirements

- C1: All entities follow the specified lifecycle/outcome separation.
- C3: Crash during each transition produces correct recovery behavior.
- C5: Identities do not encode semantic meaning.
- C8: End-to-end Execution lifecycle produces expected state transitions.

## Non-goals

- Distributed Mission execution across Forge instances.
- Real-time entity synchronization.
- Custom user-defined lifecycle states.

### R13: Lease clock authority

Lease expiry MUST use the database clock as the authoritative time source. Worker-local clocks MUST NOT be trusted for lease expiry decisions.

Monotonic duration measurements (for internal timeouts and deadlines) MAY use local monotonic clocks, but these MUST NOT be used as authoritative evidence for lease enforcement.
