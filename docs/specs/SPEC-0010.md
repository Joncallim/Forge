# SPEC-0010: Workforce Package v1

**Status:** Accepted
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the declarative Workforce package format, manifest schema, installation semantics, versioning rules, dependency management, and the boundary between package data and executable code.

## Definitions

- **Workforce package**: A versioned, content-addressed collection of declarative definitions describing a Workforce.
- **Manifest**: The root metadata file of a Workforce package.
- **Lockfile**: A file pinning exact versions and digests of all package dependencies.
- **Package pin**: The association of a specific package version/digest with a running Mission.
- **Provenance**: Verifiable origin and integrity information for a package.

## Normative requirements

### R1: Package is declarative data

A Workforce package is declarative data. It MUST NOT contain:

- Arbitrary install/runtime/lifecycle hooks.
- Embedded credentials or secrets.
- Package-executable code executed inside Forge Core.
- Shell scripts or commands executed during installation.
- Dynamic imports or code generation that runs in Core.

### R2: Install does not authorize

Package installation MUST be separate from execution authorization.

Installing a package validates its structure and records its contents.

Installation success MUST NOT imply execution authority.

### R3: Manifest schema

The package manifest MUST use JSON Schema 2020-12 and include at minimum:

| Field | Description |
|---|---|
| `packageId` | Unique package identifier (reverse-domain or URI) |
| `version` | SemVer version string |
| `description` | Human-readable description |
| `forgeCompatibility` | Compatible Forge version range |
| `roles` | Role definitions (agents in this Workforce) |
| `workflows` | Workflow orchestration templates |
| `prompts` | Prompt templates and references |
| `schemas` | Input/output/evidence schemas |
| `gates` | Additive gate definitions |
| `supportedResources` | Resource types this package can work with |
| `requiredCapabilities` | Capabilities the package requests |
| `optionalCapabilities` | Capabilities the package may use if granted |
| `cognitiveRequirements` | Cognitive class and constraints |
| `budgetProfiles` | Default budget profiles |
| `dependencies` | Other packages this depends on |
| `assets` | Reference material, examples, documentation |
| `provenance` | Origin, author, signing info |

### R4: Capability/permission expansion requires review

A package version that requests new or broader Capabilities (compared to the previously installed version) MUST require explicit operator or policy review before activation.

This applies regardless of SemVer MAJOR/MINOR/PATCH label.

### R5: Immutable package versions

Released/installed package versions MUST be immutable and content-addressed.

Two installs of the same package version MUST produce identical content.

**Source resolution**: An install request MAY name a Git branch or tag as a source reference. However, before validation and activation, the package system MUST resolve the branch/tag to an exact immutable commit/revision. The installed lock and provenance record MUST pin this exact source revision plus content digest.

**Version integrity**: If the same `packageId` + `version` is observed with a different content digest (e.g., a branch was force-pushed), the system MUST treat this as a supply-chain version conflict and MUST reject the installation. It MUST NOT silently replace prior content.

**Derived revisions**: Operator edits to an installed package MUST produce an explicit derived/local package revision (see R9) with new version identifier, parent provenance, operator identity, and timestamp. Derived revisions MUST NOT impersonate upstream SemVer identity — they must be clearly distinguishable from upstream releases.

### R6: Lockfile

A package MUST produce a lockfile that pins:

- Package version and content digest.
- Exact immutable source revision.
- All dependency packages with version and digest.
- Schema revisions used.

### R7: Dependency constraints

Dependencies MUST NOT inherit permissions.

Transitive Capability requests MUST be visible to the operator before activation.

A dependency failure MUST NOT cause silent fallback.

### R8: Package pin for running Missions

A running Mission MUST pin its package version/digest, workflow revision, prompt revisions, schema revisions, and dependency lock digest.

Updating the installed package MUST NOT alter a running or historical Mission's meaning.

### R9: Derived/local package revisions

Operator edits to an installed package MUST produce an explicit derived/local package revision with:

- New version identifier.
- Parent provenance (what was modified from).
- Operator identity.
- Timestamp.

Operator edits MUST NOT silently impersonate the upstream package version.

### R10: Distribution starts local/Git

Initial package distribution MUST support:

- Local filesystem paths.
- Git repository references (commit/tag/branch).

A public registry/marketplace is deferred.

### R11: Package signatures

Package signatures MAY prove provenance and integrity.

Signatures MUST NOT prove that a package is safe to execute.

Safety is determined by separate permission/conformance review.

### R12: SemVer for public packages

For public package compatibility:

- **MAJOR**: incompatible Workflow, interface, Resource, or Artifact change.
- **MINOR**: backward-compatible optional capability, workflow, role, or schema addition.
- **PATCH**: compatible prompt, documentation, or evaluation fix.

### R13: OCI compatibility

Package identity and storage SHOULD be compatible with OCI generic artifact conventions to enable future registry migration.

A registry MUST NOT be required in v1.

## Conceptual data model

### workforce_packages table

```
id: UUID
package_id: string (reverse-domain)
version: string (SemVer)
digest: string (SHA-256 of manifest + content)
manifest: jsonb
source_type: enum(local, git, registry)
source_ref: string (path, URL, or registry reference)
lockfile: jsonb | null
installed_at: timestamptz
installed_by: string (Principal)
provenance: jsonb
deprecated: bool
superseded_by: UUID | null
```

### mission_package_pins table

```
mission_id: UUID
package_id: UUID
workflow_revision: string
prompt_revisions: jsonb
schema_revisions: jsonb
dependency_lock_digest: string
pinned_at: timestamptz
```

### derived_package_revisions table

```
id: UUID
parent_package_id: UUID
version: string
digest: string
manifest: jsonb
operator: string
modification_notes: string | null
created_at: timestamptz
```

## Authority implications

> **Note:** The data models above are conceptual and show required semantic fields. The exact physical table layout, column types, indexes, and partitioning are implementation decisions. See the [Data Model Reference](data-model-reference.md) for ownership and consolidation.



- Package Capability requests are proposals, not authority.
- Installation requires a Grant for `package.install`.
- Activation requires a separate Grant for each requested Capability on the target Resources.
- Transitive dependency Capabilities must be reviewed before activation.

## Failure semantics

- Package validation failure → install aborted; no state change.
- Digest mismatch → install aborted; possible tampering detected.
- Dependency resolution failure → install aborted.
- Lockfile mismatch → install aborted.

## Concurrency semantics

- Package install and update MUST be serialized per package identity.
- Running Mission pin updates MUST be serialized per Mission.

## Security/privacy

- Package contents MUST be validated before any files are written.
- Embedded content MUST be scanned for secrets before install.
- Package provenance MUST be verified if signatures are present.
- Package source MUST be validated (no path traversal, no arbitrary URL fetch in v1).

## Compatibility/versioning

- Breaking manifest schema changes MUST increment the schema version.
- Forge MUST reject manifests with unknown/incompatible schema versions.

## Observability/evidence

- Every package install, update, and pin MUST be recorded.
- Package validation results MUST be evidence artifacts.
- Capability request changes between versions MUST be operator-visible.

## Conformance requirements

- C1: Package manifest validates against JSON Schema 2020-12.
- C1: Package contains no executable code.
- C2: Same source produces identical digest.
- C5: Install does not grant authority.
- C5: Package content cannot widen Grants.

## Non-goals

- Public Workforce marketplace/registry.
- Automatic trust of generated Workforces.
- Package hot-reload.
- Package rollback automation (operator-initiated only).
