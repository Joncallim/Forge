# SPEC-0006: Model Invocation & Cost Contract v1

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the governance boundary for governed model invocations, provider-neutral cognitive requirements, budget hierarchy, provider readiness taxonomy, routing rules, and cost telemetry.

## Definitions

- **Governed model invocation**: Any model invocation that consumes tokens, compute, or budget — including production cognition (within an Execution) AND active operator-initiated probes. Only synthetic/local unit-test fakes that never reach a real model provider are outside this boundary. Active operator probes MUST be accounted, budgeted, and observable through the same governance mechanisms as governed invocations, even if they use separate budget allocations or alerting thresholds.
- **Invocation boundary**: The common governance layer every production call must cross.
- **Cognitive requirement**: A provider-neutral description of the kind of cognition needed (class, reasoning depth, context size).
- **Budget hierarchy**: The layered structure of hard and soft limits governing spend.
- **Provider readiness**: The current state of a provider's ability to serve requests.
- **Routing receipt**: A durable record of why a particular provider/model was chosen.

## Normative requirements

### R1: Governed invocation boundary

Every governed model invocation (production cognition AND active operator probes) MUST cross a common governance boundary that performs, in order:

1. Identify the Principal/Mission/Execution.
2. Classify the data/Resources involved (per SPEC-0005).
3. Apply destination/provider egress policy.
4. Determine eligible provider candidates.
5. Derive a conservative budget bound.
6. Atomically reserve budget.
7. Deterministically select provider/model.
8. Construct bounded context (minimum useful context, not full history).
9. Persist a routing receipt.
10. Invoke the model.
11. Settle usage/cost/outcome.

### R2: Provider-neutral cognitive requirements

Workflows MUST request cognitive capabilities using provider-neutral declarations, not hard-coded model names.

Initial cognitive classes:

| Class | Typical use | Typical models (illustrative — SKUs will change) |
|---|---|---|
| `local` | Bounded deterministic-adjacent tasks | Local models, small quantized |
| `economy` | Extraction, triage, mechanical work, routine review | Economy-class offerings from any provider |
| `standard` | General reasoning, implementation, summarization | Standard-class offerings from any provider |
| `frontier` | Architecture, difficult diagnosis, security review | Frontier-class offerings from any provider |

> **Note on model names**: The examples above use contemporary provider SKUs for illustration only. Normative architecture specs must outlive any specific model SKU. Implementation agents MUST use the cognitive class (economy, standard, frontier) for routing decisions, not hard-coded model names. Provider-specific model names belong in operational configuration, not in architecture specs.

Cognitive constraints that MAY be specified:

- `context: low | medium | high` — estimated context requirement.
- `modality: text | code | structured | multimodal` — required modality.
- `runtime_tools: none | limited | full` — tool execution requirement.
- `data_classification: PUBLIC | INTERNAL | CONFIDENTIAL | SECRET` — per SPEC-0005.
- `latency_objective: interactive | background | batch`.
- `quality_floor: draft | review | production | auditable`.
- `local_only: bool` — must not leave local host.

### R3: No LLM selects the LLM

The deterministic router MUST select the provider and model. No LLM call is made solely to decide which LLM to invoke.

### R4: Budget hierarchy

Budgets MUST be structured hierarchically:

```
workspace/system ceiling
  → Workforce defaults
    → Mission budget
      → Execution reservation / consumption
        → Agent Run actual usage
```

Each level MUST constrain the levels below it.

### R5: Hard budget types

Forge MUST support at minimum these hard limits:

| Limit type | Description |
|---|---|
| `cost_usd` | Maximum monetary cost (where known) |
| `input_tokens` | Maximum input tokens |
| `output_tokens` | Maximum output tokens |
| `total_tokens` | Maximum sum of input + output |
| `model_calls` | Maximum number of model invocations |
| `frontier_calls` | Maximum number of frontier-class calls |
| `concurrency` | Maximum parallel invocations |
| `retries` | Maximum retry attempts |
| `remediation_depth` | Maximum depth of remediation/rework cycles |
| `wall_clock_ms` | Maximum wall-clock duration |
| `child_executions` | Maximum child Execution count |

### R6: Budget reservation

Before every model invocation, Forge MUST:

1. Derive a conservative upper bound of expected cost/usage.
2. Atomically reserve that bound from the current budget.
3. Fail the invocation if reservation would exceed a hard limit.

### R7: Parallel reservation safety

Parallel reservations MUST NOT collectively oversubscribe a hard budget.

If multiple reservations are in-flight, the sum of all active reservations plus consumed usage MUST NOT exceed the hard ceiling.

### R8: Unknown usage/cost

If provider usage or cost data is unavailable after invocation:

- The cost MUST be recorded as `UNKNOWN`.
- `UNKNOWN` MUST NOT be treated as zero.
- Under a hard monetary ceiling, unknown cost blocks further cost-incurring invocations unless a conservative bounding estimate or explicit alternative policy exists.

### R9: Routing admission order

The deterministic router MUST follow this admission order:

1. Identify Principal/Mission/Execution.
2. Classify data/Resources (SPEC-0005).
3. Apply destination/provider egress policy.
4. Determine eligible candidates based on cognitive requirements + policy + health.
5. Derive conservative budget bound.
6. Atomically reserve budget.
7. Select provider/model (deterministic policy, not LLM).
8. Construct bounded context.
9. Persist routing receipt.
10. Invoke.
11. Settle usage/cost/outcome.

### R10: Provider readiness taxonomy

Provider readiness MUST distinguish at minimum:

| State | Meaning |
|---|---|
| `ready` | Provider is healthy and accepting requests |
| `configuration_error` | Provider configuration is invalid |
| `authentication_error` | Credentials are missing, expired, or invalid |
| `quota_exhausted` | Rate or spend quota is exhausted |
| `rate_limited` | Temporarily rate-limited |
| `unreachable` | Network or DNS failure |
| `degraded` | Provider is responding but with degraded quality/latency |
| `unknown_or_stale` | No recent readiness data available |

Provider readiness evaluation MUST NOT make generative model calls.

### R11: Routing receipts

Every resolved governed model invocation MUST produce a routing receipt containing:

- Invocation identity.
- Cognitive requirements requested.
- Eligible candidates and their readiness states.
- Selection rationale (which policy rule selected the winner).
- Budget reservation details.
- Actual provider/model selected.
- Timestamp.

### R12: Optimization target

The routing optimization target MUST be:

> Minimum expected total cost to a verified outcome, subject to quality, authority, privacy, and budget constraints.

This is NOT "cheapest call." A cheap model that fails and requires rework may be more expensive than a stronger initial call.

### R13: Cost telemetry

Forge MUST expose at minimum these cost metrics:

| Metric | Description |
|---|---|
| `cost_per_verified_mission` | Total cost divided by verified Missions |
| `cost_per_verified_execution` | Total cost divided by verified Executions |
| `tokens_per_verified_outcome` | Tokens consumed per verified outcome |
| `failed_call_cost` | Cost of failed/refused/blocked calls |
| `rework_cost` | Cost attributable to rework cycles |
| `frontier_fraction` | Fraction of calls using frontier models |
| `deterministic_completion_fraction` | Fraction of completions without model calls |
| `idle_token_usage` | Tokens consumed during idle periods (target: 0) |
| `context_reuse_hit_rate` | Rate of reusable context/index hits |
| `unknown_cost_fraction` | Fraction of invocations with unknown cost |

## Conceptual data model

### budget_allocations table

```
id: UUID
parent_allocation_id: UUID | null
entity_type: enum(workspace, workforce, mission, execution, agent_run)
entity_id: UUID
limit_type: string (from R5)
hard_limit: numeric
reserved: numeric
consumed: numeric
currency: string (default: USD)
created_at: timestamptz
updated_at: timestamptz
```

### routing_receipts table

```
id: UUID
invocation_id: UUID
mission_id: UUID | null
execution_id: UUID | null
cognitive_class: string
constraints: jsonb
eligible_candidates: jsonb
selection_rationale: string
budget_reservation_id: UUID
selected_provider: string
selected_model: string
invoked_at: timestamptz
settled_at: timestamptz | null
usage: jsonb | null
cost: numeric | null
cost_unknown: bool
```

### provider_readiness table

```
provider_id: string
state: enum(ready, configuration_error, authentication_error, quota_exhausted, rate_limited, unreachable, degraded, unknown_or_stale)
observed_at: timestamptz
details: jsonb | null (redacted)
```

## Authority implications

> **Note:** The data models above are conceptual and show required semantic fields. The exact physical table layout, column types, indexes, and partitioning are implementation decisions. See the [Data Model Reference](data-model-reference.md) for ownership and consolidation.



- Model invocation requires both a Grant for the cognitive Capability and budget authorization.
- Budget is part of the effective authority computation (SPEC-0003 R4).
- Exceeding budget is equivalent to authority denial.

## Failure semantics

- Budget reservation failure → invocation denied with `budget_exhausted` reason code.
- No eligible provider → invocation denied with `no_eligible_provider` reason code.
- Provider invocation failure → routed to retry or fallback per policy.
- Unknown cost → blocks further cost-incurring invocations per R8.

## Concurrency semantics

- Budget reservations MUST use atomic operations (advisory locks or database transaction isolation).
- Parallel reservations MUST check the sum of all active reservations against the hard ceiling.

## Security/privacy

- Routing receipts MUST NOT contain raw prompt content.
- Provider readiness details MUST be redacted to avoid leaking configuration/credential information.

## Compatibility/versioning

- Existing provider health/configuration code MUST be migrated to the readiness taxonomy.
- Existing cost storage (per-run tokens/cost) remains valid; this spec aggregates rather than replaces it.

## Observability/evidence

- Every governed model invocation MUST have a routing receipt.
- Budget reservation and consumption MUST be auditable.
- Provider readiness changes MUST be logged.

## Conformance requirements

- C1: All governed invocations cross the governance boundary.
- C3: Budget state survives restart.
- C4: Parallel reservations do not oversubscribe hard limits.
- C5: Data classification check precedes provider selection.
- C7: Cost metrics are recorded and unknown cost is never forged to zero.

## Non-goals

- Model ensembles or voting.
- Latent-state bridging.
- LLM-based routing.
- Automatic provider discovery.
- FOCUS-format cost export (future compatibility only).

### R14: Provider circuit-breaking by failure class

The invocation broker MUST implement circuit-breaking or equivalent backoff for provider-level failures. Recovery semantics MUST vary by failure class:

| Failure class | Circuit-break behavior | Recovery semantics |
|---|---|---|
| `authentication_error` | Block new invocations immediately; do not retry automatically | Requires credentials/config change OR explicit non-generative readiness validation success before clearing |
| `quota_exhausted` | Stop routing; may allow invocations that are within known remaining quota | Respect known quota reset timing (e.g., rate-limit window, spend-period boundary) or operator intervention |
| `rate_limited` | Apply exponential backoff with jitter; respect Retry-After header if present | Gradually probe with backoff; half-open after cool-down |
| `unreachable` | Stop routing; apply exponential backoff; periodically probe with lightweight health check | Half-open probe after backoff period; escalate if unreachable persists beyond operator-configured threshold |
| `degraded` | Reduce routing weight; avoid routing latency-sensitive or critical Operations | Bounded avoidance with half-open recovery policy; escalate if degradation persists |
| `configuration_error` | Block new invocations; do not retry automatically | Requires configuration fix; no automatic retry storm |
| `unknown_or_stale` | Apply conservative backoff; treat as degraded until fresh readiness data available | Probe once before each routing decision until readiness confirmed |

**Generic requirements**:

- Record circuit-breaker state as provider readiness evidence (see R10).
- Prevent retry storms during provider outages — exponential backoff is mandatory.
- Preserve budget for healthy providers — do not waste reservations on broken providers.
- Provider readiness checks MUST remain zero-generative unless explicitly operator-triggered through the normal model broker (see R10).
- Do not use one generic cooldown for all failure classes — each class has distinct recovery semantics as shown above.
