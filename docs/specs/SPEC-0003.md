# SPEC-0003: Authorization & Grants v1

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines how Forge authorizes actions through Grants, the Principal + Action/Capability + Resource + Context authorization model, authority derivation, approval binding, and the relationship between pinned behaviour policy and current security policy.

## Definitions

- **Principal**: An identity acting in Forge (operator, Mission, Execution, Agent Run, Trigger, adapter, verifier, system controller).
- **Capability**: A class of action (e.g., `filesystem.read`, `github.pr.create`, `mail.send`).
- **Resource**: A thing Capabilities may act upon, identified by type and selector.
- **Grant**: A binding of Capability to Resource scope under constraints and policy for a Principal.
- **Context**: The circumstances under which an authorization check occurs (Mission, Execution, current policy revision, budget state).
- **Authority ceiling**: The maximum authority a given Principal may ever possess.
- **Pinned policy**: The behaviour-defining policy revision captured when a Mission was created or last approved.
- **Current security policy**: The live, up-to-date security policy that may revoke or restrict previously granted authority.

## Normative requirements

### R1: Authorization model

Authorization MUST follow a PARC-like model:

```
Principal + Action/Capability + Resource + Context → allow/deny
```

Default MUST be **deny** for all unspecified combinations.

### R2: Precedence

Evaluation MUST use the following precedence:

1. **Explicit deny** (from any applicable policy) — always wins.
2. **Explicit allow** (from any applicable policy) — wins unless an explicit deny applies.
3. **No applicable policy** — deny.

This is "deny overrides allow" semantics. A permit from a lower-authority source MUST NOT override a deny from a higher-authority source.

### R3: Fail-closed evaluation

If policy evaluation cannot complete due to an error (missing policy, unreachable policy store, schema mismatch), the authorization MUST fail closed (deny).

### R4: Effective authority computation

Effective authority MUST be the intersection of all applicable ceilings:

```
effective = forge_system_ceiling
           ∩ current_security_policy
           ∩ resource_policy
           ∩ operation_policy
           ∩ mission_max_authority
           ∩ parent_grant
           ∩ current_earned_autonomy_ceiling
           ∩ operator_ceiling_revocation
           ∩ budget_state_celling
           ∩ deadline_celling
```

Each intersection MUST produce a strict subset or equal envelope. No combination MAY widen authority.

### R5: Child Grant constraint

A child Grant MUST be a strict subset of, or equal to, its parent Grant's authority envelope.

```
child.authority ⊆ parent.authority
```

This MUST be enforced at Grant issuance time and MAY be rechecked at authorization time.

### R6: Sources that cannot mint authority

The following MUST NOT mint, widen, or alter authority:

- Role labels (textual names).
- Prompt prose (any model-facing instructions).
- Model output (any generated content).
- Feature flags (configuration toggles).
- Package text or metadata (Workforce descriptions, READMEs).
- External Resource contents (repository files, web content, API responses).
- Adapter responses.

### R7: Grant structure

Every Grant MUST contain at minimum:

| Field | Description |
|---|---|
| `grant_id` | Stable opaque identity |
| `revision` | Monotonic revision number |
| `principal` | The Principal receiving the Grant |
| `capability` | The Capability being granted |
| `resource_selector` | The Resource scope (type + identity + optional constraints) |
| `constraints` | Conditions, rate limits, time bounds, operation bounds |
| `parent_grant_id` | The Grant from which this is derived (null for root) |
| `mission_id` | The Mission under which this Grant is issued |
| `issuer` | The Principal that issued the Grant |
| `policy_revision` | The policy revision at issuance time |
| `issued_at` | UTC timestamp of issuance |
| `expires_at` | UTC timestamp of expiry (null = no expiry) |

### R8: Approval binding

A human approval MUST bind to:

- The exact revision/digest of the approved artifact (work package, plan, policy).
- The exact Capability scope approved.
- The exact Resource scope approved.
- The policy state at time of approval.

A material change to any of these invalidates the approval.

Approval records MUST be immutable and auditable.

### R9: Pinned behaviour vs current security

Running Missions pin the following for reproducibility:

- Workforce package version/digest.
- Workflow revision.
- Prompt/harness revision.
- Input artifact references.

However, before every new consequential action (Operation admission, model invocation, external side effect), Forge MUST re-evaluate the **current security ceiling**. A later global revoke MUST deny a previously pinned permission.

```
Pinned behaviour = deterministic reproducibility
Current security = live authority boundary
```

A Mission MUST NOT continue acting under a revoked permission even if the behaviour is pinned.

### R10: Principal types

Forge MUST support at minimum these Principal types:

| Type | Description |
|---|---|
| `operator` | Human operator with administrative authority within Forge/system security ceilings |
| `system` | Forge Core internal controller |
| `mission` | A Mission acting within its Grant envelope |
| `execution` | An Execution acting within its parent Mission's envelope |
| `agent_run` | A specific Agent Run |
| `trigger` | A Trigger acting to initiate Executions |
| `adapter` | A Capability adapter performing operations |
| `verifier` | A verification/review process |
| `service` | Internal service-to-service communication |

**Operator authority limitation**: Operator administrative authority remains subject to immutable Forge/system security ceilings and explicitly non-overridable invariants (see SPEC-0015 H1-H10). The operator cannot bypass:
- Authorization fail-closed rules (R3).
- Hard invariants (SPEC-0015 R1) — these are non-overridable by any Principal, including the operator.
- Immutable evidence rules (SPEC-0002 R8).
- Grant monotonic narrowing (R5).
- Explicit deny precedence (R2).

Operator authority is administrative, not absolute. An operator action that would violate a hard invariant MUST be blocked. There is no operator "exception" mechanism for hard invariants. If an invariant itself needs changing, that requires an explicit spec/ADR/policy revision with full review, migration, and rollback planning — not a one-off operator override.

### R11: Grant derivation chain

Grant issuance MUST follow the authority chain:

```
Operator/Workspace ceiling
  └── Mission Grant (subset of operator ceiling)
       └── Execution Grant (subset of Mission Grant)
            └── Work Package Grant (subset of Execution Grant)
                 └── Agent Run Grant (subset of Work Package Grant)
                      └── Operation admission (checked against Agent Run Grant)
```

Each derivation MUST be recorded and auditable.

### R12: Revocation

Revocation MUST be effective immediately for new authorization checks.

Revocation MUST NOT automatically roll back completed side effects.

A revoked Principal MUST NOT:

- Obtain new Grants.
- Be admitted to new Executions.
- Issue new Operations.
- Invoke new model calls.

```
id: UUID

invalidated_reason: string | null
```

## Authority implications

> **Note:** The data models above are conceptual and show required semantic fields. The exact physical table layout, column types, indexes, and partitioning are implementation decisions. See the [Data Model Reference](data-model-reference.md) for ownership and consolidation.



This spec defines the entire authorization model for Forge. All other specs MUST reference this spec for authority-related requirements.

## Failure semantics

- Policy evaluation failure → deny.
- Missing Grant → deny.
- Expired Grant → deny.
- Revoked Grant → deny.
- Unknown Principal → deny.
- Unknown Capability → deny.

## Concurrency semantics

- Grant issuance and revocation MUST be serializable (advisory lock or equivalent on the Principal).
- Approval invalidation MUST be atomic with the policy/material change that triggers it.
- **Authorization admission fencing**: Every authorization check (before Operation admission, model invocation, or external side effect) MUST bind the exact Grant revision, policy revision, and Resource version that were current at the time of admission. The authorization decision produces an **admission token** encoding these bindings. Before the consequential action executes (model invocation or external submission), the runtime MUST re-verify that the admission token's specific Grant/policy/Resource revisions are still valid — not merely that a fresh recheck would pass, but that the exact revisions relied upon have not been revoked or superseded.
- **Revocation invalidation**: When a Grant is revoked, all outstanding admission tokens issued under that Grant revision MUST be invalidated. The runtime MUST check admission token validity before allowing model invocation or external submission — not just before the initial admission check. This closes the TOCTOU window where a Grant is revoked between admission check and consequential action.
- **Lease/admission coupling**: An Execution lease MUST bind to the admission state at lease grant time. If a Grant is revoked while the lease is held, the next consequential action check MUST fail regardless of lease validity.
- **Conformance**: C4 tests MUST verify that revocation between admission→model invocation and admission→external submission correctly denies the operation. C5 tests MUST verify that admission token revision binding prevents stale-Grant execution.

## Security/privacy
## Security/privacy

- Grant records are sensitive and MUST be access-controlled.
- Approval records MUST NOT contain full policy text, only digests and references.
- Revocation MUST be logged with operator identity and reason.

## Compatibility/versioning

- Existing MCP admission/grants (ADR 0009) MUST be reconciled with this spec.
- The Grant structure MAY be extended with additional constraints without a MAJOR version change.

## Observability/evidence

- Every Grant issuance and revocation MUST produce an audit event.
- Every authorization check MUST produce a structured result (allow/deny + reason + policy references).
- Approval records MUST be durable and immutable.

## Conformance requirements

- C5: Child Grant never exceeds parent Grant.
- C5: Deny overrides allow.
- C5: Fail-closed on policy evaluation error.
- C5: Approval binding prevents reuse after material change.
- C5: Revocation prevents new actions.

## Non-goals

- Enterprise multi-user RBAC.
- Fine-grained attribute-based access control (ABAC) beyond PARC model.
- External identity provider integration.
- Delegation chains longer than Mission→Execution→Work Package→Agent Run→Operation.
