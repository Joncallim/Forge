# SPEC-0001: Specification Authoring Standard

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the mandatory structure and conventions for all normative specifications in the `docs/specs/` directory. Every spec MUST conform to this standard.

## Definitions

- **Normative requirement**: An actionable MUST, MUST NOT, SHOULD, SHOULD NOT, or MAY statement that constrains implementation.
- **Spec**: A document in `docs/specs/` that defines normative requirements.
- **ADR**: A document in `docs/adr/` that records a durable architectural decision.
- **Conformance test**: An executable test that proves whether an implementation satisfies one or more normative requirements.

## Normative requirements

### 1. Structure

Every spec MUST contain the following sections in order:

1. **Title** — SPEC-NNNN: Short Descriptive Title
2. **Status/Version** — Current status (Draft/Accepted/Superseded/Deprecated), version number, date, and supersedes reference.
3. **Scope** — What this spec covers and what it explicitly does not cover.
4. **Definitions** — Terms used in the spec with precise meanings.
5. **Normative requirements** — Numbered MUST/MUST NOT/SHOULD/SHOULD NOT/MAY statements organized by topic.
6. **Data/state model** — Entities, relationships, and lifecycle states where relevant.
7. **Authority implications** — How this spec affects the authority model (Grants, policies, ceilings).
8. **Failure semantics** — What happens when things go wrong at every meaningful transition.
9. **Concurrency semantics** — How concurrent access, leases, fencing, and race conditions are handled.
10. **Security/privacy** — Security and privacy requirements specific to this spec.
11. **Compatibility/versioning** — Version compatibility rules and migration requirements.
12. **Observability/evidence** — What evidence is produced, how it is structured, and retention rules.
13. **Conformance requirements** — What must be proven by conformance tests.
14. **Non-goals** — Things explicitly out of scope for this spec.
15. **References** — Related ADRs, specs, issues, and external standards.

### 2. Language

- Use RFC 2119 keywords (MUST, MUST NOT, SHOULD, SHOULD NOT, MAY) as defined in [RFC 2119](https://tools.ietf.org/html/rfc2119).
- Use passive voice for requirements: "The system MUST reject..." rather than "We must reject...".
- Use present tense for normative statements.
- Use future tense only for planned but not yet normative features.

### 3. Versioning

- Spec versions follow SemVer-compatible MAJOR.MINOR numbering.
- MAJOR version changes when a normative requirement is broken (a MUST becomes SHOULD, a prohibition is removed, or a previously forbidden behavior becomes permitted).
- MINOR version changes when normative requirements are added or clarified without breaking existing ones.
- Each spec version is immutable once Accepted. A new version supersedes the old one.
- Historical Executions retain the spec versions that governed them.

### 4. Cross-referencing

- Reference specs as SPEC-NNNN.
- Reference ADRs as ADR NNNN.
- Reference issues as #NNNN.
- Reference external standards by name and version/date.

### 5. Conformance

- Every normative requirement MUST be traceable to at least one conformance test class (see SPEC-0008).
- Conformance tests MUST be maintained in the repository and run as part of CI.
- A spec MAY declare requirements that are not yet testable, but MUST mark them with a future-dated review deadline.

## Data/state model

A spec's data model section MUST describe:

- Entities and their relationships.
- Lifecycle states and valid transitions.
- Identity rules (opaque vs meaningful IDs, immutability constraints).
- Persistence requirements (which store, durability class, replication).
- Versioning of data entities where applicable.

## Authority implications

A spec's authority section MUST describe:

- What new authorities (Grants, Capabilities, permissions) this spec introduces.
- How authorities interact with existing policies and ceilings.
- Default deny boundaries.
- Revocation semantics.
- Any changes to the Principal/Resource/Capability model.

## Failure semantics

A spec's failure section MUST enumerate for each consequential operation:

- What happens if the process crashes before durable intent is recorded.
- What happens if the process crashes after durable intent but before external submission.
- What happens if the external submission succeeds but local acknowledgement is lost.
- What happens on duplicate delivery.
- What happens on timeout.
- What happens on lease expiry.
- What happens on cancellation/revocation during each phase.

## Concurrency semantics

A spec's concurrency section MUST address:

- Leasing and fencing mechanisms.
- Race conditions and their prevention.
- Idempotency guarantees.
- Serialization requirements.
- Deadlock prevention.

## Observability/evidence

A spec's observability section MUST describe:

- What evidence is produced for audit vs operational telemetry.
- Evidence structure, immutability, and retention.
- Correlation IDs and linkage rules.
- Redaction/privacy requirements for evidence.
- Telemetry vs audit separation (see SPEC-0012).

## Non-goals

Every spec MUST explicitly list what it does not cover, to prevent scope creep and incorrect assumptions.
