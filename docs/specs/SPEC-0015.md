# SPEC-0015: Reliability / SLO Profile v1

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the reliability profile for Forge VNext, including hard invariants that get zero error budget, operational SLI candidates, error budget principles, and the separation between security/authority invariants and operational reliability.

## Definitions

- **Hard invariant**: A condition that must never be violated. Violation is a defect or security incident regardless of error budget.
- **SLI (Service Level Indicator)**: A quantifiable measure of a system behavior.
- **SLO (Service Level Objective)**: A target value for an SLI.
- **Error budget**: The acceptable amount of SLO violation over a time window.
- **Operational reliability**: The system's ability to perform its functions correctly over time (latency, availability, throughput).
- **Security/authority invariant**: A condition that must hold for the system to be trustworthy.

## Normative requirements

### R1: Hard invariants (zero error budget)

The following conditions MUST never occur. Any occurrence is a defect or security incident:

| # | Invariant |
|---|---|
| H1 | An unauthorized Operation is admitted and executed |
| H2 | A secret or confidential Resource is sent to a forbidden destination |
| H3 | A confirmed duplicate side effect occurs (same external mutation applied twice) |
| H4 | A child Grant is wider than its parent Grant |
| H5 | Self-verification grants authority (producer passes its own gate) |
| H6 | Unknown or missing evidence is treated as success or zero cost |
| H7 | A model call occurs on a declared zero-token path |
| H8 | A revoked Principal obtains new admission |
| H9 | Evidence is tampered with without detection |
| H10 | A package with tampered content is installed or executed |

### R2: Operational SLI candidates

Forge SHOULD measure the following operational SLIs. Specific numeric SLOs MUST NOT be set until baseline data is collected.

| SLI | Description | Measurement approach |
|---|---|---|
| Mission admission latency | Time from trigger to admitted Execution | Execution `created_at` to `admitted_at` |
| Execution wake latency | Time from queued to leased | Execution `queued_at` to `leased_at` |
| Continuation latency | Time between dependent Work Packages within an Execution | Work Package completion to next Work Package start |
| Trigger delivery latency | Time from occurrence to Execution creation | Trigger `time` to Execution `created_at` |
| Routing latency | Time for provider selection | Routing receipt `invoked_at` minus request time |
| Model broker availability | Fraction of model invocation attempts that reach a provider | Successful invocations / total attempts |
| Adapter latency | Time for adapter operations | Operation `started_at` to `terminal_at` |
| Recovery time | Time from failure detection to successful recovery | Incident start to recovery confirmation |
| Verification completion time | Time from gate trigger to gate result | Gate evaluation duration |
| Operator UI availability | Fraction of time the operator interface is responsive | Uptime monitoring |

### R3: Error budget scope

Error budgets apply to operational reliability SLIs, NOT to hard invariants (R1).

Hard invariants have **no permissible error budget**. Any violation is a defect or security incident, not an SLO miss. Error budget consumption is not a meaningful concept for hard invariants — violation triggers immediate incident response regardless of budget state.

Operational SLIs use standard error-budget semantics: a measured violation consumes a portion of the error budget; the budget may be spent down over the measurement window without triggering incident response until exhaustion.

### R4: Baseline before SLOs

Forge MUST collect baseline measurements for operational SLIs before setting numeric SLO targets.

SLO targets MUST be based on observed data, not arbitrary numbers.

The baseline period SHOULD be a representative period appropriate to the traffic and usage patterns of the system. A 30-day baseline is a common default but is not universally required — lower-traffic systems may need longer baselines; stable, well-understood systems with existing data may use shorter ones.

### R5: SLO setting criteria

When SLOs are set, they MUST:

- Be based on representative baseline data (see R4).
- Have a defined measurement window (e.g., 30-day rolling).
- Have a defined error budget.
- Be reviewed periodically (quarterly review is the recommended default policy, not an architecture invariant).
- Be documented with the rationale for the target value.

### R6: Monitoring requirements

Hard invariants MUST have real-time monitoring and alerting.

Operational SLIs SHOULD have monitoring and alerting.

Alerting SHOULD use appropriate thresholds and error-budget burn-rate logic rather than a generic "below the SLO" threshold. Burn-rate alerts trigger when the error budget is being consumed faster than expected, giving earlier warning than a simple SLO-margin threshold.

### R7: Incident response

Hard invariant violations MUST trigger immediate incident response.

Operational SLO violations SHOULD trigger incident response according to severity.

## Conceptual data model

### hard_invariant_violations table

```
id: UUID
invariant_id: string (H1-H10)
description: string
detected_at: timestamptz
detected_by: string (system component)
evidence_refs: string[]
severity: enum(critical, high)
resolved_at: timestamptz | null
resolution: string | null
incident_id: UUID | null
```

### operational_sli_measurements table

```
id: UUID
sli_name: string
value: numeric
unit: string
measured_at: timestamptz
entity_id: UUID | null (mission, execution, etc.)
dimensions: jsonb | null
```

## Authority implications

> **Note:** The data models above are conceptual and show required semantic fields. The exact physical table layout, column types, indexes, and partitioning are implementation decisions. See the [Data Model Reference](data-model-reference.md) for ownership and consolidation.



- Hard invariant violations MUST trigger immediate authority review.
- An H1 or H4 violation may require revocation of affected Grants.
- An H5 violation may invalidate affected gate decisions.

## Failure semantics

- Hard invariant violation → incident; containment first, then root cause analysis.
- SLI measurement failure → do not degrade system operation.
- Monitoring system failure → do not assume invariants are holding.

## Concurrency semantics

- Hard invariant detection MUST be atomic or use fencing to prevent false positives.
- SLI measurements MAY tolerate concurrent writes.

## Security/privacy

- Hard invariant violation details are sensitive and MUST be access-controlled.
- SLI measurements MUST NOT contain sensitive data.

## Compatibility/versioning

- New hard invariants MAY be added. Existing ones MUST NOT be removed without explicit risk acceptance.
- SLI definitions MAY evolve as the system matures.

## Observability/evidence

- Hard invariant violations are security/operations incidents and MUST produce audit events.
- SLI measurements are operational telemetry and follow SPEC-0012 rules.

## Conformance requirements

- C1: Hard invariants are documented and monitored.
- C5: Hard invariant violations trigger incident response.
- C7: Zero-token-idle violations are detected as H7.

## Non-goals

- Specific numeric SLO targets (baseline collection required first).
- Automated SLO tuning.
- User-facing reliability dashboards.
- External SLA commitments.
