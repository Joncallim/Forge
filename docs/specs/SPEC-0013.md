# SPEC-0013: Agentic Threat Model v1

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the agentic threat model for Forge VNext, mapping threats to preventive and detective controls drawn from existing Forge concepts. It benchmarks against OWASP Agentic Security and NIST AI RMF Generative AI Profile.

## Definitions

- **Threat**: A potential violation of security, authority, privacy, or reliability goals.
- **Preventive control**: A mechanism that stops a threat from materializing.
- **Detective control**: A mechanism that detects a threat after it materializes.
- **Residual risk**: The risk remaining after all controls are applied.
- **OWASP Agentic Security**: OWASP's taxonomy of security risks in LLM-based agent systems.
- **NIST AI RMF GAI**: NIST's AI Risk Management Framework, Generative AI Profile.

## Normative requirements

### R1: Threat inventory

Forge MUST address at minimum the following threats:

| # | Threat | Description |
|---|---|---|
| T1 | Goal hijacking / prompt injection | Attacker subverts agent goal via crafted input |
| T2 | Tool misuse | Agent uses a Capability beyond its intended scope |
| T3 | Identity/privilege abuse | Attacker impersonates a Principal or escalates privileges |
| T4 | Excessive agency | Agent has more Capability/Resource access than needed |
| T5 | Agentic supply-chain compromise | Malicious package or dependency compromises Forge |
| T6 | Unexpected code execution | Agent executes arbitrary code outside approved Operations |
| T7 | Credential theft | Agent or adapter leaks credentials |
| T8 | Data exfiltration | Sensitive data leaves approved boundaries |
| T9 | Context/memory poisoning | Attacker corrupts agent context to alter behavior |
| T10 | Denial of wallet | Attacker consumes budget to exhaust resources |
| T11 | Infinite loops | Agent or trigger enters unbounded recursion |
| T12 | Self-verification | Agent verifies its own work to bypass gates |
| T13 | Evidence tampering | Attacker modifies evidence to influence gate decisions |
| T14 | Replay | Attacker replays a captured request to duplicate effects |
| T15 | Sandbox escape | Agent escapes its execution confinement |
| T16 | Confused deputy | Forge is tricked into using its authority on behalf of an attacker |
| T17 | Stale authority | Agent uses a revoked or expired Grant |
| T18 | Malicious package/update | A package update introduces malicious behavior |
| T19 | Malicious external event | A crafted external event triggers unauthorized action |
| T20 | Malicious adapter response | An adapter returns crafted data that subverts Forge |

### R2: Control mapping

Each threat MUST map to at least one preventive and one detective control.

Controls MUST reference existing Forge concepts where possible rather than duplicating systems.

### R3: Threat-to-control mapping

| Threat | Preventive control | Detective control | Test (SPEC-0008) |
|---|---|---|---|
| T1 — Prompt injection | Untrusted data cannot mint authority (SPEC-0005 R7); context packet boundary | Evidence audit; gate evaluation | C5 |
| T2 — Tool misuse | Grant scoping (SPEC-0003 R4); Operation admission (SPEC-0004 R1) | Operation audit; usage anomaly detection | C5 |
| T3 — Identity/privilege abuse | Authentication (SPEC-0009 R3); child Grant constraint (SPEC-0003 R5) | Audit log review; authorization check logging | C5 |
| T4 — Excessive agency | Minimum Grant principle; resource scoping | Grant scope audit | C5 |
| T5 — Supply-chain compromise | Package provenance (SPEC-0011); content digest verification | Tamper detection; provenance validation | C5, C1 |
| T6 — Unexpected code execution | Package is declarative (SPEC-0010 R1); Operation Catalog (SPEC-0004) | Execution audit; sandbox monitoring | C5, C4 |
| T7 — Credential theft | Credential brokering (SPEC-0005 R8); audience scoping | Sentinel-secret tests (SPEC-0005 R9) | C6 |
| T8 — Data exfiltration | Egress authorization (SPEC-0005 R4); classification-based policy | Egress audit; sentinel-secret tests | C6 |
| T9 — Context/memory poisoning | Context is bounded and labelled untrusted | Evidence comparison; integrity checks | C5 |
| T10 — Denial of wallet | Budget hierarchy (SPEC-0006 R4); hard limits | Cost anomaly detection; budget audit | C7 |
| T11 — Infinite loops | Loop prevention (SPEC-0009 R8); bounded depth/count | Trigger causality audit | C4 |
| T12 — Self-verification | Producer/verifier separation (ADR 0014); independent gate | Verification independence audit | C5 |
| T13 — Evidence tampering | Immutable evidence (SPEC-0002 R8); digest verification | Evidence digest audit | C3, C5 |
| T14 — Replay | Operation idempotency (SPEC-0004 R9); dedupe keys | Duplicate detection | C4 |
| T15 — Sandbox escape | Confined execution (SPEC-0015); minimal OS access | Escape detection monitoring | C5 |
| T16 — Confused deputy | Capability/Resource separation (SPEC-0003); explicit Grants | Authorization audit | C5 |
| T17 — Stale authority | Current security recheck (SPEC-0003 R9); Grant expiry | Revocation audit | C5 |
| T18 — Malicious package/update | Package provenance (SPEC-0011); permission diff review | Update audit; capability diff logging | C5 |
| T19 — Malicious external event | Event authentication (SPEC-0009 R3); causality check | Trigger occurrence audit | C5 |
| T20 — Malicious adapter response | Untrusted data handling (SPEC-0005 R7); output validation | Adapter response validation | C5 |

### R4: Residual risk documentation

Every threat MUST have documented residual risk after controls are applied.

Residual risk MUST be assigned an owner (team or role).

### R5: Annual review

The threat model MUST be reviewed at least annually or whenever a major architectural change occurs.

## Authority implications

- The threat model informs Grant scoping, Capability classification, and security policy.
- Threats with high residual risk MAY require additional operator approval.

## Failure semantics

- A control failure is a security incident.
- Detective controls MUST alert operators within a bounded time.

## Concurrency semantics

N/A — threat model is documentation.

## Security/privacy

- The threat model itself is INTERNAL (SPEC-0005).
- Specific vulnerability details MUST be handled according to their classification.

## Compatibility/versioning

- New threats MUST be added without changing existing threat IDs.
- Control mappings MAY be updated as the system evolves.

## Observability/evidence

- Threat model review records MUST be maintained.
- Security incidents related to identified threats MUST reference the threat ID.

## Conformance requirements

- C5: All threats have preventive and detective controls.
- C5: Controls reference existing Forge concepts.
- C5: Residual risk is documented.

## Non-goals

- Formal threat model verification.
- Penetration test automation.
- Bug bounty program.
