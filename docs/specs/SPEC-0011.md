# SPEC-0011: Provenance & Supply Chain v1

**Status:** Accepted
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines provenance requirements for Workforce packages, artifacts, and configuration within Forge VNext. It covers integrity verification, source origin tracking, and supply-chain security principles without mandating a specific signing infrastructure.

## Definitions

- **Provenance**: Verifiable information about the origin, creation, and integrity of an entity.
- **Supply chain**: The sequence of sources, transformations, and transfers that produce a deployed package or artifact.
- **SLSA**: Supply-chain Levels for Software Artifacts (a security framework).
- **Attestation**: A signed statement about a package or artifact's provenance.
- **Content digest**: A cryptographic hash of the entity's content (SHA-256 minimum).

## Normative requirements

### R1: Initial provenance scope

Forge v1 MUST capture provenance for:

- Workforce package source (URI, exact commit/revision).
- Package manifest content digest.
- Asset content digests.
- Dependency lock digest.
- Forge version at installation time.
- Installer version.
- Installation actor (Principal).
- Installation timestamp.

### R2: Provenance is not safety

Provenance proves origin and integrity, not safety.

A package with verified provenance from a trusted source MAY still be unsafe.

Permission and conformance review remain separate from provenance verification.

### R3: Content addressing vs logical identity

Every installable package and artifact MUST be content-addressed.

**Content identity** (digest) identifies immutable content/blob identity. The SHA-256 digest of the canonical content uniquely identifies that specific byte sequence.

**Logical Artifact/evidence identity** is separate from content identity. Two different Agent Runs may produce byte-identical Artifacts with the same content digest but different provenance, Mission, creator, policy, and evidence lineage. These are logically distinct entities with separate identities, even though their content is identical.

**Storage optimization**: Storage MAY deduplicate blobs — content-addressable storage may store one physical copy for identical digests.

**Authority and evidence decisions**: Authority, reliability, and evidence decisions MUST use logical identity + provenance, not digest alone. A gate evaluation must consider which Agent Run produced the evidence, not just whether a matching digest exists elsewhere.

**Rule**: Two entities with the same content digest have the same **content** but are not necessarily the same **logical entity**. All normative requirements about identity, provenance, and authority refer to logical entity identity unless explicitly stated otherwise.

### R4: Provenance records

Every provenance record MUST include:

| Field | Description |
|---|---|
| `subject` | What the provenance is about (package/artifact identity) |
| `subject_digest` | SHA-256 of the subject |
| `source_uri` | Origin URI (repository URL, local path) |
| `source_revision` | Exact commit/revision/tag |
| `tree_digest` | Digest of the source tree |
| `manifest_digest` | Digest of the package manifest |
| `dependency_lock_digest` | Digest of the dependency lock |
| `forge_version` | Forge version that installed/created this |
| `installer_version` | Installer tool version |
| `actor` | Principal that performed the action |
| `timestamp` | UTC timestamp |
| `attestations` | Array of attestation references (may be empty in v1) |

### R5: Signature hooks

The provenance schema MUST include fields for future signature support:

- `signature` — cryptographic signature of the provenance (null in v1).
- `signer_identity` — identity of the signer (null in v1).
- `transparency_proof` — reference to transparency log entry (null in v1).

These fields MUST NOT be required in v1.

### R6: SLSA principles

Forge SHOULD borrow SLSA provenance principles including:

- Provenance is generated by the build/install process.
- Provenance includes all source material references.
- Provenance cannot be modified by the package being installed.

Forge MUST NOT claim a specific SLSA level without meeting all requirements for that level.

### R7: CycloneDX compatibility

CycloneDX export MAY be added later for bill-of-materials purposes.

CycloneDX MUST NOT become the authority manifest for Forge.

### R8: Tamper detection

Before using any package or artifact, Forge MUST verify:

1. The content digest matches the expected digest.
2. The provenance record is internally consistent.
3. No required field is missing or invalid.

Tampered content MUST be rejected with a `package.provenance_mismatch` reason code.

### R9: Supply chain trust

Trust in the supply chain is separate from trust in the package's runtime behavior.

A package from a verified source with valid provenance MAY still be denied execution based on policy, capability requirements, or security review.

```
id: UUID
```

## Authority implications

> **Note:** The data models above are conceptual and show required semantic fields. The exact physical table layout, column types, indexes, and partitioning are implementation decisions. See the [Data Model Reference](data-model-reference.md) for ownership and consolidation.



- Provenance verification is a precondition for package use, not a substitute for authorization.
- A package with valid provenance but denied Capabilities MUST NOT execute.
- Tampered packages MUST be rejected regardless of their requested Capabilities.

## Failure semantics

- Digest mismatch → package rejected; security event logged.
- Missing provenance → package treated as untrusted; operator decision required.
- Signature verification failure (when implemented) → package rejected.

## Concurrency semantics

- Provenance records are append-only.
- Concurrent verification of different packages is safe.

## Security/privacy

- Provenance records MUST NOT contain credentials or secrets.
- Source URIs MAY be sensitive and SHOULD be classified per SPEC-0005.

## Compatibility/versioning

- Provenance schema version is part of the record.
- New fields MUST be added as optional.

## Observability/evidence

- Provenance verification results MUST be evidence artifacts.
- Tamper detection events MUST be logged as security events.

## Conformance requirements

- C1: Provenance records include all required fields.
- C5: Tampered content is rejected.
- C5: Valid provenance does not bypass authorization.

## Non-goals

- Full SLSA Level 2+ compliance.
- Public transparency log integration.
- Build-system attestation generation.
- Dependency graph export.
