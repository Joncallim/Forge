# SPEC-0014: Migration & Compatibility v1

**Status:** Accepted
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the migration methodology, compatibility requirements, dual-write rules, historical evidence preservation, and the Project/Task→Mission/Execution migration strategy.

## Definitions

- **Structural migration**: A change to database schema, entity definitions, or data format.
- **Semantic migration**: A change to the meaning or interpretation of data.
- **Dual-write**: Temporarily writing to both old and new representations.
- **Shadow compare**: Running old and new logic in parallel and comparing results without switching authority.
- **Compatibility seam**: An interface that allows old and new code to coexist during migration.
- **Historical evidence**: Data created under a previous schema or policy.

## Normative requirements

### R1: Default migration sequence

Structural migrations MUST follow this sequence unless an explicit exception is documented:

1. **EXPAND** — Add new schema/entities alongside existing ones. Old code continues to use old schema.
2. **BACKFILL / ADAPT** — Populate new schema from old data. Adapt old readers/writers to understand new schema where needed.
3. **SHADOW COMPARE** — Run old and new paths in parallel. Compare results; do not switch authoritative read yet.
4. **SWITCH AUTHORITATIVE READ** — New schema becomes authoritative for reads. Old schema continues to accept writes for rollback safety.
5. **VERIFY** — Validate that all consumers are reading from the new authority and producing correct results.
6. **CONTRACT OLD SURFACE** — Remove old schema, old write paths, and compatibility code.

### R2: Single authority rule

There MUST NOT be co-equal permanent dual truth.

At any point, each data entity MUST have exactly one authoritative representation.

Temporary dual-write periods are acceptable only during migration (R1 steps 2-4).

### R3: Dual-write requirements

A temporary dual-write period MUST declare:

- Explicit canonical owner (which system is authoritative).
- Secondary projection (how the non-authoritative representation is derived).
- Reconciliation mechanism (how inconsistencies are detected and resolved).
- Observable divergence policy (what happens if the two representations disagree).

### R4: Migration declaration

Every migration MUST declare:

| Property | Description |
|---|---|
| Forward compatibility | Can new code read old data? |
| Backward compatibility | Can old code read new data? |
| Rollback point | What state must be preserved to allow rollback? |
| Evidence compatibility | Are historical evidence records still interpretable? |
| Historical read behavior | How old records appear through new interfaces? |
| Data preservation | Is old data preserved, transformed, or deleted? |

### R5: Historical evidence preservation

Historical evidence MUST NOT be rewritten to appear as if it was created under a new policy or schema.

Evidence created under old rules MUST carry metadata indicating the governing schema/policy version.

Evidence interpretation MUST account for the governing version at creation time.

### R6: Unknown enum/input handling

For enum fields or controlled inputs:

- An unknown value in a security-authority context MUST fail closed (deny, reject).
- An unknown value in a display or read-only context MUST be explicitly represented as unknown.
- Unknown MUST NOT be mapped to a permissive default or success.

### R7: Project/Task→Mission migration

The migration from Project/Task to Mission/Execution MUST:

1. Keep Project/Task as a compatibility surface.
2. Introduce Mission/Execution as the internal representation.
3. Map Project→Mission and Task→Execution/Work Package.
4. NOT create permanent dual truth (Task truth + Mission truth synchronized).
5. Allow new code paths to use Mission/Execution directly.
6. Allow old code paths to continue using Project/Task through the compatibility seam.

### R8: Rollback safety

Every migration MUST have a documented rollback procedure.

The rollback point MUST be tested before the migration is applied to production.

Rollback MUST restore the previous authoritative representation without data loss.

### R9: Migration testing

Migrations MUST be tested with:

- Forward migration test (old schema → new schema).
- Rollback test (new schema → old schema).
- Data preservation test (all data survives migration intact).
- Historical evidence readability test (old evidence is still interpretable).
- Dual-write consistency test (during migration window).

## Data/state model

### migration_registry table

```
id: UUID
migration_name: string
from_version: string
to_version: string
status: enum(pending, expanding, backfilling, shadow_comparing, authoritative_switched, verifying, contracted, rolled_back, failed)
started_at: timestamptz
completed_at: timestamptz | null
rolled_back_at: timestamptz | null
dual_write_canonical: string | null
rollback_point: string | null
operator: string
notes: string | null
```

## Authority implications

- Migration must not change authority semantics without an explicit spec change.
- Historical evidence must remain authoritative for its governing policy version.
- Unknown enums in authority context must fail closed.

## Failure semantics

- Migration failure → rollback to previous state.
- Dual-write inconsistency → alert operator; use canonical source.
- Data loss during migration → incident; restore from backup.
- Historical evidence corruption → incident; restore from immutable store.

## Concurrency semantics

- Migrations MUST be serialized (one at a time).
- Dual-write operations MUST be atomic or idempotent.
- Shadow compare MUST NOT affect production state.

## Security/privacy

- Migration processes MUST have the minimum necessary database access.
- Historical evidence access controls MUST survive migration.
- Rollback procedures MUST NOT expose sensitive data.

## Compatibility/versioning

- Schema versions are tracked in the migration registry.
- Evidence records reference their governing schema version.
- API versions may change independently of schema versions.

## Observability/evidence

- Every migration step MUST be logged.
- Dual-write inconsistencies MUST produce audit events.
- Rollback events MUST be recorded as security incidents.

## Conformance requirements

- C1: Migration follows the EXPAND→BACKFILL→SHADOW→SWITCH→VERIFY→CONTRACT sequence.
- C3: Rollback preserves data and returns to previous correct state.
- C5: Historical evidence is not rewritten.
- C5: Unknown enums in authority context fail closed.

## Non-goals

- Automated migration rollback.
- Zero-downtime migration (downtime is acceptable with notice).
- Cross-Forge-instance migration.
- Long-term dual-write (permanent dual truth).
