# SPEC-0012: Observability vs Audit v1

**Status:** Proposed (freeze candidate)
**Version:** 1.0
**Date:** 2026-09-04
**Supersedes:** None

## Scope

This specification defines the separation between authoritative audit/evidence data and operational telemetry, correlation conventions, privacy-safe defaults, and OpenTelemetry mapping.

## Definitions

- **Audit/evidence data**: Immutable, policy-governed records used for authority verification, recovery, and compliance.
- **Operational telemetry**: Sampleable, retention-limited data used for debugging, performance analysis, and operations.
- **Span**: A named, timed operation representing a unit of work (OpenTelemetry concept).
- **Metric**: A measured value about a system behavior (OpenTelemetry concept).

## Normative requirements

### R1: Audit/evidence primacy

Audit/evidence data MUST be:

- Unsampled according to policy.
- Stored in durable, access-controlled systems.
- Used for authority, recovery, and verification decisions.
- Immutable after finalization.

### R2: Telemetry loss tolerance

Telemetry loss MUST NEVER change Mission, Execution, Operation, or Grant truth.

If telemetry cannot be produced, the system MUST continue operating correctly.

Telemetry write failures MUST NOT block or degrade authoritative operations.

### R3: Correlation identifiers

All observability outputs (both audit and telemetry) MUST carry at least one of these correlation identifiers where applicable:

| Identifier | Applied to |
|---|---|
| `forge.mission_id` | Mission-scoped work |
| `forge.execution_id` | Execution-scoped work |
| `forge.work_package_id` | Work Package-scoped work |
| `forge.agent_run_id` | Agent Run-scoped work |
| `forge.operation_id` | Operation-scoped work |
| `forge.trigger_occurrence_id` | Trigger-scoped work |

### R4: High-cardinality avoidance

Telemetry MUST NOT explode high-cardinality dimensions such as:

- Individual file paths.
- Full prompt texts.
- Full model responses.
- Resource bodies.
- Credential values.
- Unbounded user identifiers.

### R5: OpenTelemetry mapping

Forge SHOULD map operational telemetry to OpenTelemetry conventions where sensible.

Forge MUST keep its canonical audit/evidence semantics independent, because GenAI/agent-specific OpenTelemetry conventions are still evolving.

### R6: Default telemetry privacy

Default telemetry MUST NOT export:

- Raw prompts or prompt fragments.
- Raw model responses.
- Resource bodies or contents.
- Credentials or secrets.
- Internal file paths.
- Personal identifiable information (PII).

Export of such data MUST require explicit classification (per SPEC-0005) and explicit opt-in.

### R7: Recommended spans

Forge SHOULD create spans for:

| Span | Description |
|---|---|
| `forge.mission` | Mission lifecycle |
| `forge.execution` | Execution lifecycle |
| `forge.work_package` | Work Package execution |
| `forge.model_invocation` | Model/agent invocation |
| `forge.operation` | Operation/tool execution |
| `forge.adapter` | Capability adapter call |
| `forge.gate` | Gate evaluation |
| `forge.trigger` | Trigger processing |
| `forge.reconciliation` | Side-effect reconciliation |

### R8: Recommended metrics

Forge SHOULD expose metrics for:

| Metric | Description |
|---|---|
| `forge.execution.latency_ms` | Execution duration |
| `forge.operation.latency_ms` | Operation duration |
| `forge.model.latency_ms` | Model invocation duration |
| `forge.model.tokens.input` | Input token count |
| `forge.model.tokens.output` | Output token count |
| `forge.model.call_count` | Number of model invocations |
| `forge.adapter.failure_count` | Adapter failure count |
| `forge.queue.delay_ms` | Queue wait time |
| `forge.trigger.delay_ms` | Trigger processing delay |
| `forge.budget.holds` | Budget hold count |
| `forge.reconciliation.count` | Reconciliation count |
| `forge.zero_token_idle.violations` | Zero-token-idle violations |

## Conceptual data model

### audit_events table

```
id: UUID
event_type: string (namespaced, e.g., "grant.issued", "execution.terminal")
correlation: jsonb { mission_id, execution_id, operation_id, ... }
principal: string
payload_digest: string (SHA-256 of the authoritative payload)
payload_ref: string | null (reference to full payload in evidence store)
recorded_at: timestamptz
retention_days: int
```

### telemetry configuration (not in DB)

Telemetry configuration is operational configuration, not authoritative state.

## Authority implications

> **Note:** The data models above are conceptual and show required semantic fields. The exact physical table layout, column types, indexes, and partitioning are implementation decisions. See the [Data Model Reference](data-model-reference.md) for ownership and consolidation.



- Audit events are evidence for authority decisions.
- Telemetry MUST NOT be used for authority decisions.
- Audit event loss is a security/operations incident.

## Failure semantics

- **Audit write failure before consequential external submission**: If authoritative audit/evidence persistence fails before a consequential external side effect has been submitted, the associated Operation MUST fail or block. The external action MUST NOT proceed without the required audit record.
- **Audit write failure after external submission may have occurred**: If the external submission may already have happened and the confirmation/audit persistence is lost, the Operation MUST NOT report business failure. Instead, it MUST transition to `submission_uncertain` (see SPEC-0004 R4), evidence-degraded, or equivalent recovery state. The system MUST reconcile actual external state before retry. Reporting failure when the side effect may have succeeded would create incorrect business state.
- **Required audit/durable intent that must exist before a consequential effect SHOULD be persisted before submission where possible**.
- **Telemetry write failure** → MUST NOT affect the associated operation. Telemetry is non-authoritative.
- **Cross-reference**: See SPEC-0004 R4 for the side-effect lifecycle states and SPEC-0004 R6 for submission_uncertain reconciliation.

## Concurrency semantics

- Audit events are append-only; no concurrency conflicts.
- Telemetry aggregation MAY tolerate concurrent writes.

## Security/privacy

- Default telemetry MUST be privacy-safe (no prompts, no resource bodies).
- Audit events are sensitive and MUST be access-controlled.
- Retention policies MUST be enforced for both audit and telemetry.

## Compatibility/versioning

- Audit event schema is versioned.
- Telemetry metric names SHOULD follow OpenTelemetry naming conventions.

## Observability/evidence

- This spec defines the observability of observability: audit events about audit system health SHOULD be produced.

## Conformance requirements

- C3: Telemetry loss does not affect operations.
- C5: Default telemetry does not export sensitive data.
- C5: Audit events are immutable and access-controlled.

## Non-goals

- Mandating a specific OpenTelemetry backend or exporter.
- Real-time telemetry streaming to external systems.
- User-facing analytics dashboards (operational dashboards only).
